# Delta Lake in Databricks — Complete Guide

## 1. What is Delta Lake?

**Delta Lake** is an open-source storage layer that sits on top of cloud/object storage such as:

* Amazon S3
* Azure Data Lake Storage (ADLS)
* Google Cloud Storage (GCS)

It adds **database-like capabilities** to data stored as files, especially Parquet.

### Simple definition

> **Delta Lake = Parquet files + Transaction Log + ACID transactions + data management features**

In Databricks, Delta Lake is the **default table format** for most workloads.

```text
                Databricks / Spark
                       |
                       v
              +------------------+
              |    Delta Lake    |
              +------------------+
                 /            \
                /              \
        Parquet files       _delta_log
           (.parquet)          |
             Data         Transaction history
```

---

# 2. Why do we need Delta Lake?

Suppose you have raw data stored in S3.

```text
s3://company-data/
    sales/
       part-0001.parquet
       part-0002.parquet
       part-0003.parquet
```

Parquet is excellent for analytics, but by itself it doesn't provide many database features.

For example:

* What if two jobs write at the same time?
* What if a job fails halfway through?
* How do we update one customer's record?
* How do we delete records?
* How do we know which files belong to the current table version?
* How do we go back to yesterday's data?
* How do we safely perform concurrent reads and writes?

Delta Lake solves these problems using a **transaction log**.

---

# 3. Delta Lake Architecture

A Delta table generally looks like this:

```text
S3
│
└── sales/
    │
    ├── part-00001.parquet
    ├── part-00002.parquet
    ├── part-00003.parquet
    ├── part-00004.parquet
    │
    └── _delta_log/
        ├── 00000000000000000000.json
        ├── 00000000000000000001.json
        ├── 00000000000000000002.json
        ├── 00000000000000000003.json
        └── ...
```

There are two important parts:

### 1. Data files

Usually Parquet files.

```text
part-00001.parquet
part-00002.parquet
part-00003.parquet
```

These contain the actual data.

### 2. `_delta_log`

This contains the transaction history of the Delta table.

```text
_delta_log/
    00000000000000000000.json
    00000000000000000001.json
    00000000000000000002.json
```

The transaction log tells Delta which files are currently part of the table.

# 4. Delta Lake vs Parquet

| Feature             | Parquet | Delta Lake |
| ------------------- | ------- | ---------- |
| Columnar storage    | ✅       | ✅          |
| Compression         | ✅       | ✅          |
| ACID transactions   | ❌       | ✅          |
| UPDATE              | Limited | ✅          |
| DELETE              | Limited | ✅          |
| MERGE               | ❌       | ✅          |
| Time Travel         | ❌       | ✅          |
| Schema enforcement  | Limited | ✅          |
| Schema evolution    | Limited | ✅          |
| Transaction history | ❌       | ✅          |
| Concurrent writes   | Limited | ✅          |
| Streaming support   | ✅       | ✅          |
| Batch processing    | ✅       | ✅          |

Important:

> Delta Lake does **not replace Parquet**. Delta Lake normally uses Parquet as the physical data-file format and adds the transaction-log layer.

# 5. What is `_delta_log`?

This is one of the most important concepts for interviews.

Suppose the table initially contains:

```text
A.parquet
B.parquet
```

Delta transaction log might record:

```text
Version 0

ADD A.parquet
ADD B.parquet
```

Now you update some records.

Delta may create new files:

```text
C.parquet
D.parquet
```

and mark old files as removed.

```text
Version 1

REMOVE A.parquet
REMOVE B.parquet

ADD C.parquet
ADD D.parquet
```

The original files may physically remain temporarily, but Delta knows that the **current table version** consists of:

```text
C.parquet
D.parquet
```

# 6. ACID Transactions

Delta Lake provides **ACID transactions**.

## ACID

### A — Atomicity

A transaction either succeeds completely or does not become visible.

Example:

```text
Transaction:

File A → written
File B → written
File C → FAILED
```

The incomplete transaction shouldn't appear as a partially committed table state.

---

### C — Consistency

The table remains in a valid state after a transaction.

---

### I — Isolation

Concurrent operations are handled so readers don't see an inconsistent partial state.

---

### D — Durability

Once a transaction is committed, its committed state is recorded in the transaction log.

# 7. How Delta Writes Work

Suppose you execute:

```python
df.write.format("delta").mode("append").save("/data/sales")
```

Conceptually:

```text
DataFrame
   |
   v
Spark writes Parquet files
   |
   v
New files created
   |
   v
Delta transaction committed
   |
   v
_delta_log updated
```

The transaction log records the new files.

# 13. MERGE

`MERGE` is one of the most important Delta Lake features.

It is commonly used for **upsert** operations.

### Upsert

```text
If record exists
      |
      +---- UPDATE

If record doesn't exist
      |
      +---- INSERT
```

Example:

```sql
MERGE INTO customers AS target
USING updates AS source
ON target.id = source.id

WHEN MATCHED THEN
    UPDATE SET *

WHEN NOT MATCHED THEN
    INSERT *;
```

---

# 14. Real-Time Example of MERGE

Suppose your existing Delta table contains:

```text
id | name | salary
---|------|-------
1  | John | 50000
2  | Bob  | 60000
3  | Alex | 70000
```

New incoming data:

```text
id | name | salary
---|------|-------
2  | Bob  | 65000
4  | Sam  | 55000
```

After:

```sql
MERGE INTO employees t
USING updates s
ON t.id = s.id

WHEN MATCHED THEN
UPDATE SET *

WHEN NOT MATCHED THEN
INSERT *;
```

Result:

```text
id | name | salary
---|------|-------
1  | John | 50000
2  | Bob  | 65000
3  | Alex | 70000
4  | Sam  | 55000
```

# 15. Time Travel

One of the biggest advantages of Delta Lake is **Time Travel**.

Delta maintains table versions.

```text
Version 0
Version 1
Version 2
Version 3
Version 4
```

You can query older versions.

```sql
SELECT *
FROM sales VERSION AS OF 3;
```

You can also query by timestamp:

```sql
SELECT *
FROM sales
TIMESTAMP AS OF '2026-09-25 10:00:00';
```

---

# 16. Why Time Travel Is Useful

Imagine someone accidentally executes:

```sql
DELETE FROM customers;
```

Instead of immediately losing the historical table state, Delta's transaction history can allow you to inspect an earlier version.

```text
Current
   |
   v
Version 5 → Wrong DELETE

Previous
   |
   v
Version 4 → Correct data
```

You can inspect:

```sql
SELECT *
FROM customers VERSION AS OF 4;
```

---

# 17. Important: Time Travel ≠ Permanent Backup

This is important.

Time travel depends on retention and cleanup settings.

For example:

```sql
VACUUM customers;
```

can remove old data files that are no longer needed.

Therefore:

> Don't treat Delta Time Travel as a replacement for a long-term backup strategy.

---

# 18. VACUUM

Delta tables can accumulate old files.

Example:

```text
Version 1
   |
   +-- old-file-1.parquet

Version 2
   |
   +-- old-file-2.parquet

Version 3
   |
   +-- current-file.parquet
```

Old files may no longer be needed.

`VACUUM` removes obsolete data files after the configured retention period.

```sql
VACUUM sales;
```

You can specify retention:

```sql
VACUUM sales RETAIN 168 HOURS;
```

168 hours = 7 days.

---

# 19. VACUUM vs Time Travel

```text
Time Travel
     |
     +--- allows access to historical versions
     
VACUUM
     |
     +--- removes obsolete physical data files
```

So:

```text
More VACUUM cleanup
        ↓
Less historical data available
```

# 22. Partitioning

You can partition a Delta table.

Example:

```python
df.write \
  .format("delta") \
  .partitionBy("year", "month") \
  .save("/data/sales")
```

Storage might look like:

```text
sales/
│
├── year=2025/
│   ├── month=01/
│   ├── month=02/
│   └── month=03/
│
└── year=2026/
    ├── month=01/
    ├── month=02/
    └── month=03/
```

---

# 23. Partition Pruning

Suppose you query:

```sql
SELECT *
FROM sales
WHERE year = 2026
AND month = 9;
```

Spark can avoid scanning unrelated partitions.

Instead of:

```text
2025
2026
2027
```

it can focus on:

```text
2026 / 09
```

This is called **partition pruning**.

---

# 24. Don't Over-Partition

A common mistake is partitioning by high-cardinality columns.

Bad example:

```python
.partitionBy("customer_id")
```

if you have millions of customers.

You can create huge numbers of small files/directories.

Better candidates are often:

```text
year
month
date
```

depending on the workload.

---

# 25. Small File Problem

Suppose streaming or frequent batch jobs keep writing:

```text
file1.parquet
file2.parquet
file3.parquet
...
file100000.parquet
```

Many tiny files cause performance problems.

```text
Too many small files
        ↓
More file listing
        ↓
More metadata overhead
        ↓
More task scheduling
        ↓
Slower queries
```

Delta/Databricks provides optimization techniques to deal with this.

---

# 26. OPTIMIZE

`OPTIMIZE` compacts small files into larger files.

```sql
OPTIMIZE sales;
```

Conceptually:

```text
Before:

A.parquet
B.parquet
C.parquet
D.parquet
E.parquet
...

        ↓ OPTIMIZE

After:

large-file-1.parquet
large-file-2.parquet
```

---

# 27. Z-Ordering

Z-Ordering can improve data skipping for frequently filtered columns.

Example:

```sql
OPTIMIZE sales
ZORDER BY (customer_id);
```

Suppose queries frequently use:

```sql
WHERE customer_id = 123
```

Z-Ordering can organize related data to improve skipping.

Note:

> Z-Ordering is not the same thing as partitioning.

---

# 28. Data Skipping

Delta stores statistics about data files.

For example:

```text
File A
min(customer_id) = 1
max(customer_id) = 100

File B
min(customer_id) = 1000
max(customer_id) = 2000
```

Query:

```sql
WHERE customer_id = 50
```

Delta can determine that:

```text
File A → possible match
File B → impossible
```

So File B can potentially be skipped.

This is called **data skipping**.

# 48. Delta Lake Transaction Example

Let's understand the internal idea.

Initial table:

```text
Version 0

A.parquet
B.parquet
```

Transaction log:

```text
00000000000000000000.json
```

contains actions conceptually like:

```text
ADD A
ADD B
```

Now an update happens.

```sql
UPDATE customers
SET city = 'Bangalore'
WHERE id = 10;
```

Spark may write a new Parquet file:

```text
C.parquet
```

and commit:

```text
Version 1

REMOVE old-file
ADD C.parquet
```

Current table state becomes:

```text
C.parquet
B.parquet
```

The old physical file can remain until cleanup.

# 49. Optimistic Concurrency Control

Delta Lake uses transaction mechanisms to handle concurrent operations.

Imagine:

```text
Job A ──────────────┐
                    |
                    v
                 Delta
                    ^
                    |
Job B ──────────────┘
```

Both jobs may attempt to commit.

Delta checks whether the transaction is still valid against the table state.

If there is a conflict, one operation may need to retry/fail rather than silently corrupting the table.

```text
               v
              S3
```

Example:

```python
df = spark.read.format("delta").load(path)

result = df.groupBy("customer_id").sum("amount")

result.write.format("delta").mode("overwrite").save(output)
```

# 58. Interview Question: What is Delta Lake?

### Good answer

> Delta Lake is an open-source storage layer for data lakes that provides ACID transactions, schema enforcement, schema evolution, time travel, MERGE/upsert capabilities, and reliable batch and streaming processing. It commonly stores data as Parquet files and maintains a transaction log in `_delta_log`. In Databricks, Delta Lake is commonly used to build reliable lakehouse architectures.

---

# 59. Interview Question: Why use Delta instead of Parquet?

Answer:

> Parquet provides efficient columnar storage, but Delta Lake adds transactional capabilities on top of Parquet, including ACID transactions, schema enforcement, updates, deletes, merges, time travel, and transaction history.

---

# 60. Interview Question: What is `_delta_log`?

Answer:

> `_delta_log` is the transaction log of a Delta table. It records changes to the table, such as files added and removed, metadata changes, and transaction information. Delta uses this log to determine the current consistent state of the table and support features such as time travel and ACID transactions.

---

# 61. Interview Question: What happens during UPDATE?

Simplified:

```text
UPDATE
  |
  v
Find affected files
  |
  v
Read affected records
  |
  v
Create new Parquet files
  |
  v
Commit transaction
  |
  v
_delta_log updated
  |
  v
Old files become obsolete
```

Later:

```text
VACUUM
```

can remove eligible obsolete files.

---

# 62. Interview Question: What is MERGE?

Answer:

> `MERGE` allows us to implement conditional inserts, updates, and deletes in a Delta table. It is commonly used for upsert operations and CDC pipelines.

---

# 63. Interview Question: What is Time Travel?

Answer:

> Time Travel allows us to query previous versions of a Delta table using a version number or timestamp. Delta achieves this through its transaction history and retained data files.

Example:

```sql
SELECT *
FROM sales VERSION AS OF 10;
```

---

# 64. Interview Question: What is VACUUM?

Answer:

> `VACUUM` removes obsolete data files that are no longer required by the Delta table according to the retention policy. It helps control storage consumption, but aggressive cleanup can reduce the ability to access older table versions.
