# Unity Catalog — Ordered Summary

## 1. Why Do We Need a Metadata Store?

First, the lecture starts with a basic question: **what is metadata and why do we need a metadata store?**

When Spark reads data directly from S3, you need to know:

* File location
* File format — Parquet, Delta, CSV, JSON, etc.
* Schema
* Column names
* Data types

Instead of repeatedly providing all this information, we create a **table**.

```text
SELECT * FROM orders
```

Spark still needs to know:

```text
orders
 ├── Location
 ├── Format
 ├── Schema
 ├── Columns
 └── Data types
```

That information is stored in a **metadata store**. 

---

# 2. Hive Metastore → Spark → Databricks

The lecture then explains the history.

### Hive

Apache Hive needed metadata to register tables on HDFS.

So Hive created:

```text
Hive
  ↓
Hive Metastore
  ↓
Relational DB
(MySQL/PostgreSQL)
```

The metastore stored things such as:

* Table name
* Storage location
* File format
* Schema

### Spark

Spark did not initially create a completely new metadata system.

It adopted the **Hive Metastore**.

```text
Hive Metastore
      ↓
Apache Spark
```

Spark therefore inherited the Hive metadata model. 

### Databricks

Databricks brought Spark and its Hive Metastore into the Databricks workspace.

Initially:

```text
Databricks Workspace
      │
      └── Hive Metastore
              │
              └── Table metadata

Cloud Storage
      │
      └── Actual data
          (S3)
```

This worked well when there was basically **one workspace/team**. 

---

# 3. Problem With Hive Metastore

As organizations grew, they started creating multiple workspaces:

```text
Dev Workspace
UAT Workspace
Production Workspace
Analytics Workspace
Data Engineering Workspace
```

The problem was:

```text
Workspace A
   ↓
Hive Metastore A

Workspace B
   ↓
Hive Metastore B
```

A table created in Workspace A wasn't automatically visible in Workspace B.

So every workspace became an isolated **silo**.

The lecture identifies three major problems:

### Problem 1 — Workspace silos

A table in Workspace A wasn't visible in Workspace B.

### Problem 2 — No unified permissions

Permissions were workspace-specific.

There wasn't one centralized permission model across all workspaces.

### Problem 3 — No lineage

Hive Metastore didn't provide information such as:

```text
Where did this data come from?
Which pipeline created it?
Who queried it?
How did this table get produced?
```

These problems led Databricks to introduce **Unity Catalog**. 

---

# 4. Unity Catalog Architecture

Unity Catalog redesigned the metadata-management system.

The basic hierarchy is:

```text
Unity Catalog Metastore
          │
          ├── Catalog
          │      │
          │      └── Schema
          │             │
          │             ├── Tables
          │             ├── Views
          │             ├── Volumes
          │             └── Functions
          │
          └── ...
```

The **Metastore** is at the top.

It is associated with the Databricks account and can be shared across workspaces. 

### Catalog

Catalog is mainly a namespace/grouping layer.

Examples:

```text
dev
uat
prod
```

or:

```text
finance
marketing
sales
```

### Schema

Inside a catalog:

```text
catalog
   ↓
schema
   ↓
tables/views/volumes/functions
```

# 5. Workspace Relationship With Unity Catalog

The lecture then explains that **workspace and Unity Catalog are separate concepts**.

Example:

```text
                Databricks Account
                       │
                Unity Catalog
                       │
                  Metastore
                 /    |     \
                /     |      \
             Dev     UAT     Prod
          Workspace Workspace Workspace
```

Workspaces are connected to the common metastore.

Then catalogs can be made available to specific workspaces.

Example:

```text
Dev Workspace
   ↓
dev catalog

UAT Workspace
   ↓
dev catalog

Prod Workspace
   ↓
prod catalog
```

So access can be organized by environment.

After creating:

* S3 buckets
* External locations

the next step is creating:

```text
dev catalog
prod catalog
```

The external locations are configured as the storage locations for the catalogs.

Therefore:

```text

    ↓

    ↓
dev S3 bucket
```

and:

```text

    ↓
prod external location
    ↓

```

The storage location defined at the catalog level is inherited by objects created under it.

# 12. User Management

Next, the lecture moves from infrastructure to **users and security**.

Databricks/Unity Catalog has three main principals:

### 1. Users

Real human users.

```text

dev2
test1
test2
prod1
```

### 2. Groups

Groups represent teams.

Example:

```text
DBX_ENG
DBX_UAT

```

### 3. Service Principals

Non-human identities used for automation.

Example:

```text

```

The lecture strongly emphasizes that production jobs should not depend on an individual user's credentials because users can leave/change roles. Service principals are intended for automation.

# 15. Workspace Admin — Important Gotchas

The next lecture tests what a workspace admin can actually do.

A workspace admin can technically create catalogs and external locations.

But there is an important limitation.

For example, if an account admin created a catalog:

```text
dev catalog
```

the workspace admin may be able to see it but cannot automatically manage it.

They need appropriate permissions on that catalog.

Similarly, creating a useful external-location-backed catalog requires access to the underlying cloud storage and required permissions.

Therefore, in practice:

```text
Account Admin
      OR
Metastore Admin
       ↓
Often creates catalogs/external locations
```

while:

```text
Workspace Admin
       ↓
Mostly workspace administration
```



The lecture also emphasizes that workspace admins handle workspace-level configuration and membership.

# 16. Unity Catalog Permission Hierarchy

Now the lecture moves into the **permission model**.

Hierarchy:

```text
Metastore
   ↓
Catalog
   ↓
Schema
   ↓
Table / View / Volume / Function
```

Permissions can be granted at different levels.

The lecture follows the **least-privilege** approach.

Don't give users broad permissions at a high level unless necessary.

For example, granting a permission at the catalog level may affect schemas/objects underneath it.

# 19. Tables vs Volumes

The final lecture goes inside the schema and introduces two important objects:

```text
Schema
 ├── Tables
 └── Volumes
```

### Table

Used for structured data:

```text
Rows + Columns
```

Examples:

```text
orders
customers
products
```

Semi-structured JSON can also be handled inside tables using types such as Variant.

### Volume

Used for files, particularly unstructured data.

Examples:

```text
Images
Videos
Text files
Other files
```

A volume provides a directory-like location that is governed by Unity Catalog permissions. 

---

# 20. Table Permissions

The lecture uses three major table permissions:

### SELECT

Allows reading/querying table data.

### MODIFY

Allows modifying table data.

### MANAGE

Highest-level privilege in the example.

Can allow operations such as:

* Transfer ownership
* Rename
* Drop/manage the table

The development group receives:

```text
SELECT
MODIFY
MANAGE
```

The testing group receives:

```text
SELECT
MODIFY
```



---

# 21. Volume Permissions

Similarly, volumes have:

### READ VOLUME

Read files from the volume.

### WRITE VOLUME

Create/write files and directories.

### MANAGE

Administrative control such as ownership/rename/delete operations.

The example gives:

```text
Development:
READ VOLUME
WRITE VOLUME
MANAGE

Testing:
READ VOLUME
WRITE VOLUME
```

# 23. Why Unity Catalog Was Introduced

The lecture ultimately comes back to the original Hive Metastore problems.

### Hive Metastore

```text
Workspace A → Metadata A
Workspace B → Metadata B
Workspace C → Metadata C
```

This creates silos.

### Unity Catalog

```text
             Account
                │
            Metastore
                │
       ┌────────┼────────┐
       │        │        │
     Dev      UAT      Prod
   Workspace Workspace Workspace
```

One centralized metadata/security layer can serve multiple workspaces.

The lecture highlights the main benefits:

1. **Breaks workspace silos**
2. **Centralized permission model**
3. **Automatic lineage**
4. **Fine-grained access control**
5. **Volumes for file governance**
6. **Governance of tables/files through Unity Catalog**
