# Spark Declarative Pipeline (SDP) — Complete Summary

This chapter moves from **Lakeflow Connect (Ingestion)** to the **Transform pillar: Lakeflow Spark Declarative Pipeline (SDP)**.

The lectures progress in this order:

```text
Lakeflow
├── Connect       → Ingestion
├── SDP           → Transformation
└── Jobs          → Orchestration
```

---

## 1. Why SDP exists

You can already build pipelines using normal Spark:

```text
Read source
   ↓
Transform
   ↓
Write target
```

But with traditional Spark, **you manage all the orchestration yourself**:

* Execution order
* Incremental processing
* Retry logic
* Data quality
* CDC ordering
* Dependencies
* Checkpoints
* Pipeline scheduling
* Failure handling

So a small amount of business logic can become surrounded by lots of infrastructure/orchestration code.

### SDP solves this

Instead of telling Spark **how to execute everything**, you declare **what you want the final data products to be**.

Example:

> "I want a Silver Orders table containing the cleaned CDC data from Bronze."

SDP determines:

* dependency order
* execution plan
* incremental processing
* retry/processing mechanics
* pipeline graph

### Mental model

```text
Imperative Spark
"You do these steps in this order"

             VS

Declarative SDP
"I want these tables/flows to exist"
                    ↓
             SDP plans execution
```

The lecture compares this to SQL: you describe the result and the engine decides how to execute it.

---

# 2. DLT → SDP history

The framework was originally called:

**Delta Live Tables (DLT)**

The lecture explains that the declarative pipeline engine was subsequently brought into the Apache Spark ecosystem as **Spark Declarative Pipelines**, while Databricks' managed implementation is called **Lakeflow Spark Declarative Pipeline (SDP)**.

Older Databricks documentation/code may therefore contain **DLT**, but the chapter uses the newer SDP APIs and terminology.

---

# 3. Standalone pipeline vs Lakeflow SDP

There are two related approaches.

### Standalone pipeline

Databricks SQL can create things such as:

* Streaming tables
* Materialized views

without explicitly creating/managing an SDP pipeline.

Good for:

* Simple SQL transformations
* Small use cases
* Analyst-driven workloads

### Lakeflow SDP

You explicitly manage:

* Pipeline
* Source code
* Flows
* Data quality
* CDC
* Compute
* Dependencies
* Pipeline graph

Better suited to a **multi-layer production data pipeline**.

### Simple decision

```text
Simple SQL object
       ↓
Standalone

Complex production pipeline
       ↓
Lakeflow SDP
```

# 4. SDP core vocabulary

There are three major concepts:

```text
Pipeline
   │
   ├── Flow
   │     ├── Source
   │     ├── Transformation
   │     └── Destination
   │
   └── Flow
```

### Pipeline

The **container/project**.

Contains:

* Source code
* Catalog/schema
* Compute configuration
* Pipeline configuration
* Multiple flows

When you run the pipeline, SDP analyzes all source files and builds the execution graph.

The source describes the flow structure and dependencies; the pipeline is the unit of development/execution. 

---

# 5. Four SDP flow types

The chapter introduces four flows:

| Flow                       | Source       | Target                 | Creation             | Typical use                               |
| -------------------------- | ------------ | ---------------------- | -------------------- | ----------------------------------------- |
| **Append Flow**            | `readStream` | Streaming table / Sink | Implicit or Explicit | Bronze ingestion                          |
| **Auto CDC Flow**          | `readStream` | Streaming table        | Explicit             | Silver CDC                                |
| **Materialized View Flow** | `read`       | Materialized view      | Implicit             | Gold                                      |
| **Update Flow**            | `readStream` | Sink                   | Explicit             | Streaming aggregations to Kafka/Event Hub |

The source confirms these combinations and creation styles.  

---

# 6. Append Flow

## Purpose

Used when you simply want to **append incoming records**.

Typical:

```text
Cloud Files
   ↓
Auto Loader
   ↓
Append Flow
   ↓
Bronze Streaming Table
```

Source uses:

```python
spark.readStream
```

Possible streaming sources:

* Auto Loader
* Kafka
* Streaming table

Targets:

* Streaming table
* External sink

Append flow supports:

### Implicit

```python
@dp.table
def bronze_orders():
    return spark.readStream...
```

### Explicit

```python
dp.append_flow(...)
```

The lecture recommends the implicit approach when there is **one source → one target**. 

---

# 7. Why explicit Append Flow?

Suppose:

```text
Orders Source ───────┐
                     ├──→ bronze_events
Returns Source ──────┘
```

Multiple sources need to write into the **same target**.

Then use explicit append flows:

```text
create streaming table
        ↓
append flow #1 → bronze_events
append flow #2 → bronze_events
```

This is the main reason for choosing explicit append flow over implicit flow in the lecture.

---

# 8. Append Flow → External Sink

Append flow can also send data to external systems.

Example:

```text
Silver Orders
     ↓
Append Flow
     ↓
Kafka
```

You create a sink and then use an append flow to send streaming records to it.

---

# 9. Auto CDC Flow

This is the important flow for **CDC-based Silver layers**.

Architecture:

```text
Bronze CDC
    ↓
Auto CDC
    ↓
Silver Streaming Table
```

Auto CDC:

* Reads streaming data
* Handles CDC
* Handles out-of-order events
* Supports SCD Type 1
* Supports SCD Type 2
* Handles insert/update/delete semantics

It is **explicit only**.

```python
dp.create_auto_cdc_flow(...)
```

The flow definition includes things such as:

* Target
* Source
* Primary key
* `sequence_by`
* Delete condition
* SCD type
* Excluded columns

The lecture specifically uses `TSMS` as the sequence column and `OP = 'D'` / deleted flag to identify deletes. 

---

# 10. Auto CDC — important parameters

### Primary key

Used to identify the record.

Example:

```text
order_id
```

### `sequence_by`

Determines event ordering.

Example:

```text
TSMS
```

This helps Auto CDC deal with late/out-of-order CDC events.

### `apply_as_deletes`

Example:

```text
OP = 'D'
OR
__deleted = true
```

### `stored_as_scd_type`

```text
1 → SCD Type 1
2 → SCD Type 2
```

### `except_column_list`

Used to remove CDC/bronze metadata from Silver.

Example:

```text
OP
TSMS
__deleted
_ingest_timestamp
_source_file
```

---

# 11. Materialized View Flow

Materialized View (MV) flow is primarily for the **Gold layer**.

Architecture:

```text
Silver Orders ────┐
                  ├──→ Gold Materialized View
Silver Customers ─┘
```

It uses:

```python
spark.read
```

NOT:

```python
spark.readStream
```

because MV is a **batch-style transformation**.

Sources can include:

* Delta tables
* Streaming tables
* Other materialized views
* Temporary views

Target:

```text
Materialized View
```

Creation:

```python
@dp.materialized_view
```

It is **implicit only**. 

---

# 12. MV incremental refresh

You write the transformation as if it were a normal full query:

```text
Read Silver
   ↓
Join
   ↓
Filter
   ↓
Aggregate
   ↓
Return result
```

You don't manually write incremental logic.

SDP's MV engine determines whether it can perform an incremental refresh.

If it cannot, it can perform a full refresh.

So the developer focuses on **correctness of the query**, rather than manually implementing incremental refresh logic.

---

# 13. Update Flow

Update Flow is described as **preview** in the lecture.

Purpose:

> Send continuously changing/updated aggregation results to an external sink.

Example:

```text
Bronze/Silver
     ↓
Streaming aggregation
     ↓
Update Flow
     ↓
Kafka / Event Hub
```

Why not just Append Flow?

Because Append Flow is append-oriented.

If an aggregate changes:

```text
Completed orders = 100
        ↓
new data arrives
        ↓
Completed orders = 105
```

the external sink may need the **updated result**, not simply another independent append.

Update Flow is designed for this type of use case.

---

# 14. Temporary View

Temporary views are for **intermediate reusable logic**.

They:

* Exist only inside the pipeline
* Are not published as Unity Catalog tables
* Don't materialize data
* Help avoid unnecessary intermediate tables

Example:

```text
Silver
  ↓
Temporary View
  ↓
 ┌───────────────┬───────────────┐
 ↓               ↓               ↓
Gold Revenue   Gold Customer   Gold Product
```

Useful when several Gold outputs share the same intermediate transformation.

# 15. SDP Python API

The basic import:

```python
from pyspark import pipelines as dp
```

### Destination decorators

```python
@dp.table
```

Streaming table.

```python
@dp.materialized_view
```

Materialized view.

```python
@dp.temporary_view
```

Temporary view.

### Data quality

```python
@dp.expect
```

Log violation but keep record.

```python
@dp.expect_or_drop
```

Drop invalid record.

```python
@dp.expect_or_fail
```

Fail the pipeline when the expectation is violated.

### Flow functions

```python
dp.append_flow(...)
```

```python
dp.create_auto_cdc_flow(...)
```

```python
dp.update_flow(...)
```

# 16. Destination types

There are four important destination types.

| Destination           | Purpose                            |
| --------------------- | ---------------------------------- |
| **Streaming Table**   | Incremental streaming processing   |
| **Materialized View** | Stored batch/analytical result     |
| **Temporary View**    | Intermediate reusable logic        |
| **Sink**              | External destination such as Kafka |

### Rule of thumb

```text
Bronze → Streaming Table
Silver → Streaming Table
Gold   → Materialized View
Intermediate → Temporary View
External streaming → Sink
```

# 17. Hands-on: Building the Medallion SDP Pipeline

The practical section builds:

```text
CDC Files
   ↓
Bronze
   ↓
Silver
   ↓
Gold
```

The pipeline is created in a source-controlled folder so that the pipeline code is organized with Git/source control. The Databricks pipeline editor provides a Python-file-based development environment. 

Typical structure:

```text
SDP Medallion Pipeline/
│
├── transformations/
│   ├── bronze.py
│   ├── silver.py
│   └── gold.py
│
├── explorations/
├── utilities/
└── tests/
```

Only the configured transformation source path is treated as pipeline source code; exploration files are intended for development/testing rather than normal pipeline execution. 

---

# 18. Bronze Layer

Input:

```text
Landing Volume
├── orders/
└── customers/
```

Files are assumed to be generated from a CDC ingestion tool such as Debezium.

CDC fields include:

```text
OP
TSMS
__deleted
customer_id / order_id
...
```

Where:

```text
C = Create
U = Update
D = Delete
```

The Bronze requirement is:

> Preserve the CDC events as they arrive.

So:

```text
Landing files
     ↓
Auto Loader
     ↓
Bronze Streaming Tables
```

No business transformation.

---

# 19. Bronze flow implementation

Use:

```python
@dp.table
```

because:

* one source
* one target
* simple append ingestion

Example conceptual structure:

```text
Orders files
    ↓
readStream + Auto Loader
    ↓
bronze_orders_cdc
```

and:

```text
Customer files
    ↓
readStream + Auto Loader
    ↓
bronze_customer_cdc
```

Bronze tables contain the CDC events and metadata. The pipeline automatically manages the streaming mechanics instead of requiring the developer to manually configure all the traditional streaming plumbing. 

---

# 20. Bronze Data Quality

Bronze normally has minimal quality enforcement because its purpose is to preserve source data.

But critical structural fields can have expectations.

Example:

```text
OP must be C/U/D
```

The lecture uses `expect` here so that an invalid CDC operation is **reported rather than dropped**.

This protects the raw/audit nature of Bronze while highlighting ingestion problems.

---

# 21. Silver Layer

Silver is where CDC becomes business-usable data.

Architecture:

```text
Bronze CDC
     ↓
Auto CDC
     ↓
Silver Orders
Silver Customers
```

The practical implementation uses:

```text
Auto CDC
+
SCD Type 2
+
Data Quality
```

Auto CDC is explicitly created in two steps:

```text
1. Create streaming target
2. createAutoCDCFlow()
```

The lecture's Silver implementation uses this exact pattern. 

---

# 22. Silver data quality

Example rules:

### Orders

```text
order_id IS NOT NULL
customer_id IS NOT NULL
amount > 0
```

Invalid records are dropped.

This means:

```text
Bronze
  ↓
Auto CDC
  ↓
DQ checks
  ↓
Silver
```

The Silver layer therefore represents **cleaner and usable business data**.

# 24. What SCD Type 2 does

Suppose:

```text
Alice
Tier = Silver
```

Later:

```text
Alice
Tier = Gold
```

Silver keeps history:

```text
Alice | Silver | __START_AT | __END_AT
Alice | Gold   | __START_AT | NULL
```

The old record is closed and the new record becomes current.

For deletes, the lecture demonstrates **ending the historical record instead of physically deleting it**.

# 25. Gold Layer

Gold uses:

```python
@dp.materialized_view
```

Example:

```text
Silver Orders ───────┐
                     ├──→ Gold Daily Revenue
Silver Customers ────┘
```

The example calculates:

* Total revenue
* Number of orders
* Average order value

grouped by:

```text
order_date
customer_tier
```

The Gold implementation reads Silver using `spark.read` and performs the join/aggregation.

# 26. Complete pipeline graph

After adding Gold:

```text
             ┌──→ Silver Orders ────┐
Bronze Orders ──────────────────────┤
                                    ├──→ Gold Daily Revenue
Bronze Customers ─→ Silver Customers┘
```

The important point:

**You did not manually configure these dependencies.**

SDP analyzes the source/target relationships and automatically creates the DAG.

```text
Bronze
  ↓
Silver
  ↓
Gold
```

The lecture demonstrates that the pipeline graph automatically identifies these dependencies.

# 27. Incremental processing

Initially:

```text
Batch 1
 ↓
Bronze
 ↓
Silver
 ↓
Gold
```

Run the pipeline again without new data:

```text
No new data
     ↓
No new streaming records
```

Then upload Batch 2:

```text
Batch 2
 ↓
Bronze captures new CDC events
 ↓
Silver applies CDC
 ↓
Gold reflects current result
```

This demonstrates the major benefit of the declarative/incremental pipeline model.

# 28. Production Gotchas

These are especially important for interviews.

### 1. Exploration compute can differ

Exploration files are separate from pipeline execution and can run using different compute.

So don't assume:

```text
Exploration compute = Pipeline compute
```

---

### 2. `sequence_by` must properly order CDC events

Auto CDC depends on the sequence column to determine event ordering.

If two events can have the same timestamp, a single timestamp may not be enough.

The lecture recommends considering a composite sequence when necessary.

Example conceptually:

```text
(TSMS, another_sequence_column)
```

---

### 3. Be explicit with `except_column_list`

Don't accidentally push CDC metadata into Silver:

```text
OP
TSMS
__deleted
_ingest_timestamp
_source_file
```

Otherwise these implementation details can propagate into downstream Gold data.

---

### 4. Deleting source files can affect pipeline tables

The lecture highlights an important production risk:

```text
Delete transformation source file
          ↓
Table definition disappears
          ↓
Pipeline may remove inactive table
```

Therefore, understand the pipeline's **inactive-table/drop configuration** before deleting transformation files.

---

### 5. Source folders must be configured

If you create:

```text
transformations_v2/
```

but don't configure it as a pipeline source directory, SDP won't evaluate those files.

---

### 6. Expectations before Auto CDC

If an expectation/drop rule is applied to a streaming source before Auto CDC processing:

```text
Incoming CDC event
       ↓
Expectation
       ↓
Drop if invalid
       ↓
Auto CDC
       ↓
Silver
```

A rejected CDC event never reaches Auto CDC.

Therefore, monitor expectation violations because rejected CDC events can create gaps in the downstream history.

# 29. Final SDP Decision Matrix

| Requirement                          | Use                    |
| ------------------------------------ | ---------------------- |
| Cloud files → Bronze                 | **Append Flow**        |
| Kafka → Bronze                       | **Append Flow**        |
| One source → one target              | **Implicit Append**    |
| Multiple sources → same target       | **Explicit Append**    |
| CDC → Silver                         | **Auto CDC**           |
| SCD Type 1                           | **Auto CDC**           |
| SCD Type 2                           | **Auto CDC**           |
| Aggregation → Gold                   | **Materialized View**  |
| Shared intermediate logic            | **Temporary View**     |
| Append data → Kafka                  | **Append Flow + Sink** |
| Updating aggregation → external sink | **Update Flow**        |

## Interview one-liner

> **Lakeflow SDP is a declarative transformation framework where we define pipelines, flows, destinations and data-quality rules, while SDP automatically handles dependency planning and incremental execution. Typically, Append Flow is used for Bronze ingestion, Auto CDC for Silver CDC/SCD processing, Materialized Views for Gold analytics, and Temporary Views for reusable intermediate logic.**

This entire chapter's hands-on ends with a **single SDP Medallion pipeline containing multiple Bronze, Silver and Gold flows**, with SDP automatically building the dependency graph and processing new CDC batches incrementally.
