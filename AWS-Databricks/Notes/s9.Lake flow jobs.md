# Lakeflow Jobs — Ordered Summary

## 1. Lakeflow has 3 pillars

```text
Lakeflow
│
├── Lakeflow Connect
│   → Ingestion
│
├── Spark Declarative Pipelines (SDP)
│   → Transformation
│
└── Lakeflow Jobs
    → Orchestration
```

The previous chapters covered **Connect + SDP**. This chapter focuses on **Lakeflow Jobs**, which turns the pipeline into a production workflow.

---

# 2. Why do we need orchestration?

You already have a Medallion pipeline:

```text
Source
  ↓
Bronze
  ↓
Silver
  ↓
Gold
```

You can manually run the SDP pipeline from the pipeline editor.

But manual execution is not production-ready.

Someone would have to:

* Log into Databricks
* Click Run
* Monitor execution
* Restart failures
* Remember to run it every day

If new data arrives at 3 AM and nobody runs the pipeline, nothing happens.

### Orchestration solves this

```text
Lakeflow SDP
    ↓
Builds/transforms data

Lakeflow Jobs
    ↓
When/how/what should run
```

Lakeflow Jobs provides:

* Scheduling
* Dependencies
* Notifications
* Retries
* Parameters
* Conditional branching
* Repair runs
* Programmatic/API execution

A useful mental model from the lecture:

> **Notebook run = exploration; Job run = production deployment.**

A production job should be **repeatable, observable, alertable, and repairable**.

---

# 3. Three core concepts

## 3.1 Job

The **top-level container**.

It owns:

* Tasks
* Dependencies
* Schedule/trigger
* Parameters
* Notifications
* Permissions
* Other job configuration

Think:

```text
Job
│
├── Task A
├── Task B
├── Task C
│
├── Dependencies
├── Trigger
├── Parameters
└── Notifications
```

---

## 3.2 Task

A task is one unit of work inside a job.

Examples:

* Run SDP pipeline
* Run notebook
* Run Python script
* Execute SQL
* Run dbt
* Run JAR
* Run Python wheel

For Data Engineering, the three most important are:

```text
Pipeline Task
Notebook Task
Python Script Task
```

---

## 3.3 Trigger

A trigger determines **when the job starts**.

Common triggers:

```text
Schedule
File arrival
Table update
Continuous
Manual
```

Examples:

```text
Every day at 2 AM
        ↓
      Job

New file arrives
        ↓
      Job

Delta table changes
        ↓
      Job
```

---

# 4. Important task types

## Pipeline Task

Used to execute an **SDP pipeline**.

This is the correct way to operationalize your Medallion SDP pipeline.

```text
Lakeflow Job
     ↓
Pipeline Task
     ↓
SDP Pipeline
     ↓
Bronze → Silver → Gold
```

### Important

The lecture explicitly says:

> If you are running a Lakeflow SDP pipeline, use a **Pipeline Task**.

Don't wrap the SDP pipeline inside a Notebook Task.

---

## Notebook Task

Used for:

* Data quality checks
* Validation
* Reporting
* Spark/DBUtils code
* Custom notebook logic

Example:

```text
Pipeline Task
      ↓
DQ Notebook Task
```

---

## Python Script Task

Used for code that belongs in a `.py` file instead of a notebook.

Examples:

* Utility scripts
* Alerting
* Reporting
* File management
* Post-processing

```text
DQ Notebook
     ↓
Python Report Script
```

---

# 5. Triggers

### Schedule trigger

For regular batch processing:

```text
Every day at 2 AM
Every hour
Every week
```

### File arrival trigger

Runs when a new file arrives in cloud storage.

### Table update trigger

Runs when a Delta table changes.

Conceptually:

```text
Job A
  ↓
updates Delta table
  ↓
Job B
  ↓
table update trigger
```

### Manual trigger

Used during development/testing or manual execution.

# 8. Notifications

Job notifications can be configured for events such as:

* Job failure
* Job success
* Job start
* Duration warning

The lecture chooses:

```text
Job failure
     ↓
Email notification
```

rather than receiving unnecessary success emails.

# 9. Duration warning and timeout

Two useful production controls:

### Duration warning

Example:

```text
Expected runtime = 15 minutes
Warning threshold = 30 minutes
```

If:

```text
Runtime > 30 min
```

→ send warning.

### Timeout

Example:

```text
Timeout = 60 minutes
```

If the job runs for more than an hour:

```text
Job
 ↓
60 min
 ↓
Terminate
```

This helps identify stuck or unusually slow jobs.

# 10. Job parameters

Hardcoding environment-specific values is a bad production practice.

Example:

```python
catalog = "dev"
schema = "step_right"
```

When moving:

```text
DEV → TEST → PROD
```

you would need to modify code.

Instead:

```text
Job Parameter
     ↓
catalog
schema
run_date
environment
batch_id
```

The same code can run in different environments.

The lecture uses `run_date` as the main example. 

---

# 11. Four parameter mechanisms

Lakeflow Jobs provides four mechanisms:

```text
1. Job Parameters
2. Task Parameters
3. Dynamic Value References
4. Task Values
```

---

## 11.1 Job Parameters

Defined at the job level.

Example:

```text
run_date = 2026-10-02
```

They are automatically pushed down to tasks that support job parameters.

```text
Job
 │
 │ run_date
 ├─────────────→ Pipeline Task
 │
 └─────────────→ Notebook Task
```

Use when multiple tasks need the same value. 

---

## 11.2 Task Parameters

Used when a parameter belongs only to one task.

Example:

```text
DQ task
 └── threshold = 100
```

Other tasks don't need to receive it.

---

# 12. Dynamic Value References

These are values generated by Databricks during job/task execution.

Examples mentioned:

```text
Job ID
Job name
Run ID
Repair count
Trigger type
Task name
Task run ID
Task execution count
Notebook path
```

They can be used in task configuration.

A particularly useful example:

```text
{{job.parameters.run_date}}
```

This allows a job parameter to be passed to a task configuration, especially useful for Python script task arguments. 

---

# 13. Task Values

Task values are different from job parameters.

### Job parameter

Known **before the job runs**.

Example:

```text
run_date = 2026-10-02
```

### Task value

Calculated **during the job run**.

Example:

```text
DQ Task
   ↓
row_count = 125
   ↓
Downstream Task
```

The lecture summarizes it as:

> One task calculates a value and passes it to another task.



---

# 14. Notebook parameters

Notebook tasks can receive parameters using:

```python
dbutils.widgets
```

Example conceptually:

```python
dbutils.widgets.text("run_date", "")
run_date = dbutils.widgets.get("run_date")
```

Then:

```python
df = spark.table("gold_daily_revenue")

df = df.filter(
    df.order_date == run_date
)
```

This allows the DQ check to validate **only the current run date**, instead of checking the entire historical table.

That is important because:

```text
Historical rows = 1000
Today's rows = 0
```

A simple:

```python
count > 0
```

would incorrectly pass because of yesterday's 1000 records.

Filtering by `run_date` fixes this. 

---

# 15. Python Script parameters

Python scripts **don't use notebook widgets**.

Instead, Lakeflow Jobs passes parameters as command-line arguments:

```python
sys.argv
```

Example:

```text
Job parameter
     ↓
Dynamic value reference
     ↓
Python script arguments
     ↓
sys.argv
```

The lecture's key distinction:

```text
Notebook Task
    ↓
dbutils.widgets

Python Script Task
    ↓
sys.argv
```



---

# 16. Task Value example

The DQ notebook calculates:

```text
row_count = 125
```

It publishes:

```python
dbutils.jobs.taskValues.set(
    key="row_count",
    value=row_count
)
```

Then downstream Python script retrieves it:

```python
dbutils.jobs.taskValues.get(
    taskKey="DQ check gold",
    key="row_count",
    debugValue=0
)
```

Flow:

```text
Pipeline
   ↓
DQ Check Gold
   │
   │ row_count = 125
   ↓
DQ Report
```

The task name and key must match the values used when setting/getting the task value.

# 18. Branching / Conditional Workflow

The next lecture expands the simple workflow into a **multi-DAG**.

Final concept:

```text
                    SDP Pipeline
                         ↓
                  DQ Check Gold
                    /       \
                 FAIL       SUCCESS
                  ↓            ↓
              DQ Alert    Check Threshold
                              /      \
                         >= 100       < 100
                            ↓            ↓
                       DQ Report    Low Data Warning
```

This teaches two different types of branching:

### Success/failure branching

```text
Task
├── Success → Path A
└── Failure → Path B
```

### Conditional branching

```text
IF row_count >= 100
    ↓
DQ Report

ELSE
    ↓
Low Data Warning
```

# 19. DQ Alert

If the DQ task itself fails:

```text
DQ Check
   ↓
FAIL
   ↓
DQ Alert
```

The alert can:

* Send email
* Call an API
* Write an audit record
* Send to PagerDuty/alerting system

The example simply prints an alert message.

---

# 20. Threshold check

Suppose expected daily Gold output is:

```text
>= 100 rows
```

Then:

```text
row_count >= 100
       │
   ┌───┴────┐
  YES       NO
   ↓         ↓
Report    Low-data warning
```

Important distinction:

**Low data isn't necessarily a pipeline failure.**

It is a condition worth investigating.

---

# 21. Retries

Retries should be used for **transient failures**.

Possible configuration:

```text
Original attempt
      ↓
Failure
      ↓
Retry 1
      ↓
Retry 2
```

You can configure:

* Number of retries
* Wait/cooldown between retries
* Automatic/serverless retry optimization

Example:

```text
1 retry = 2 total attempts
```

The lecture removes retries from DQ tasks because a DQ failure represents a **data-quality problem**, not a transient infrastructure failure.

Instead:

```text
DQ failure
    ↓
DQ Alert
```



---

# 22. Backfill

Backfill means running the same job for **historical parameter values**.

Normal execution:

```text
March 1
   ↓
March 2
   ↓
March 3
```

But suppose the pipeline was stopped from:

```text
Feb 1 → Feb 25
```

You need to process those missing dates.

Backfill:

```text
Same Job
   │
   ├── run_date = Feb 1
   ├── run_date = Feb 2
   ├── run_date = Feb 3
   ├── ...
   └── run_date = Feb 25
```

So a backfill is essentially:

> Run the same job repeatedly for multiple parameter values.



---

# 23. Repair Runs

Another important production feature.

Suppose:

```text
Task A ✅
Task B ✅
Task C ❌
Task D didn't run
```

Don't restart everything.

Use:

```text
Repair Run
```

so that successful tasks aren't unnecessarily rerun.

Benefits:

* Saves compute
* Saves time
* Avoids unnecessary processing
* Reduces possibility of duplicate effects

The lecture explicitly recommends repair runs for production failures.

# 24. Programmatic job execution

Jobs don't have to be triggered only through the UI or schedule.

Two programmatic options:

```text
Databricks REST API
Databricks CLI
```

Architecture:

```text
AWS Lambda / External System
          ↓
Databricks REST API
          ↓
Lakeflow Job
```

or:

```text
Shell Script
     ↓
Databricks CLI
     ↓
Lakeflow Job
```

This is useful when an external event should trigger a Databricks workflow. 

---

# 25. REST API flow

The lecture demonstrates:

```text
1. Authenticate
       ↓
2. Find Job ID
       ↓
3. Call Run Now API
       ↓
4. Pass job parameters
       ↓
5. Receive Run ID
       ↓
6. Poll Run Status
```

Conceptually:

```text
External Application
       ↓
REST API
       ↓
Job ID + run_date
       ↓
Lakeflow Job
       ↓
Run ID
       ↓
Monitor status
```

The run can then be monitored using the returned Run ID.  

---

# 26. CLI

The same job can be triggered using the Databricks CLI.

Conceptually:

```text
databricks jobs list
        ↓
Find Job ID

databricks jobs run-now
        ↓
Job ID + parameters
        ↓
Job starts
```

Useful when integrating Databricks jobs with shell scripts or external automation.

# 27. Production decision rules

## Task selection

```text
SDP Pipeline
     ↓
Pipeline Task

DQ / Spark / DBUtils
     ↓
Notebook Task

Utility / Alert / Python file
     ↓
Python Script Task
```

---

## Parameter selection

```text
Used by many tasks
      ↓
Job Parameter

Used by one task
      ↓
Task Parameter

Databricks-generated runtime value
      ↓
Dynamic Value Reference

Calculated during execution
      ↓
Task Value
```

---

## Control flow

```text
Transient infrastructure failure
      ↓
Retry

Data-quality failure
      ↓
Don't blindly retry
      ↓
Alert/investigate

Success/failure path
      ↓
Run-if conditions

Runtime business condition
      ↓
If/else branching

Partial job failure
      ↓
Repair Run

Historical processing
      ↓
Backfill
```

## Interview one-liner

> **Lakeflow Jobs is the orchestration layer of Databricks Lakeflow. A Job contains Tasks, dependencies, triggers, parameters and operational controls. Pipeline Tasks run SDP pipelines, Notebook Tasks handle validation/DQ logic, and Python Script Tasks handle utility/reporting code. Production workflows can use schedules, parameters, task values, retries, conditional branching, backfills, repair runs, notifications, and REST API/CLI triggers.**

### The easiest way to remember the whole Lakeflow framework

```text
Lakeflow
│
├── Connect
│     └── "How do I get data in?"
│
├── SDP
│     └── "How do I transform data?"
│
└── Jobs
      └── "When/how should everything run?"
```

That is the **big picture** connecting the three chapters.
