# Lakeflow Data Ingestion — Final Summary

This lecture is the **chapter summary of Lakeflow Connect / Data Ingestion**. The main goal is to understand how different source types are brought into the **Bronze layer** using the appropriate connector.

---

## 1. Lakeflow Data Ingestion — Big Picture

Lakeflow provides three connected pillars:

```text
Lakeflow
│
├── Lakeflow Connect
│      → Data Ingestion
│
├── Spark Declarative Pipelines
│      → Data Transformation
│
└── Lakeflow Jobs
       → Orchestration
```

This chapter focused on **Lakeflow Connect**, whose job is to ingest data into the Bronze layer. 

---

# 2. Lakeflow Connect Architecture

For normal sources such as SaaS applications and cloud files:

```text
Source
  ↓
Connection
  ↓
Ingestion Pipeline
  ↓
Unity Catalog Bronze Table
```

### Connection

Authenticated connection to the source.

### Ingestion Pipeline

Uses the connection and incrementally brings new data.

### Destination

Unity Catalog-governed Bronze tables.

For databases, the architecture becomes slightly more complex:

```text
Database
   ↓
Connection
   ↓
Gateway
   ↓
Staging
   ↓
Ingestion Pipeline
   ↓
Bronze Table
```

The gateway continuously captures database changes, while the ingestion pipeline can run independently from the staging area. 

---

# 3. Why Gateway + Staging for CDC?

A database doesn't provide the same simple incremental API that many SaaS applications provide.

For CDC, the gateway:

```text
Database Transaction Log
          ↓
       Gateway
          ↓
      Staging Area
```

The gateway runs continuously and captures changes.

The ingestion pipeline:

```text
Staging
   ↓
Bronze
```

can be scheduled separately.

### Main advantage

If the ingestion pipeline fails:

```text
Gateway
   ↓
Staging  ← data is still safe
   ↓
Pipeline retry
   ↓
Bronze
```

So captured changes aren't lost just because the ingestion pipeline was temporarily unavailable.

# 4. Three Connector Tiers

Lakeflow Connect has three connector categories:

```text
1. Managed
2. Standard
3. Community
```

### Managed Connectors

* No-code
* Databricks-managed
* Minimal maintenance
* Handles incremental reads
* Handles retries
* Handles schema evolution
* For databases, can provide gateway + CDC

Best when a suitable connector is available.

### Standard Connectors

* Some coding required
* More flexibility
* Important example: **Auto Loader**
* Also includes streaming connectors such as Kafka/Kinesis

### Community Connectors

* Open-source
* Maintained outside Databricks
* No Databricks SLA
* Used when managed/standard options don't fit

The main tradeoff is:

```text
Managed
  ↓
Less effort / less flexibility

Standard
  ↓
More effort / more flexibility

Community
  ↓
Most ownership/risk
```

Example:

```text
Salesforce
```

Use:

```text
Managed Connector
```

Usually the simplest approach.

```text
SaaS
 ↓
Managed Connector
 ↓

```

---

# 6. B. Database

First ask:

> **Is there a managed CDC connector available and GA for this database?**

### If YES

Use:

```text
Managed CDC
```

You get the gateway, staging and ingestion pipeline with less implementation effort.

### If NO

Consider:

```text
Query-based Connector
```

This avoids CDC infrastructure.

Conceptually:

```text
Database
   ↓
Query
   ↓
Find new/changed records
   ↓
Bronze
```

The query-based approach is schedule-based rather than continuously reading transaction logs.

For example, the lecture demonstrated PostgreSQL using query-based ingestion. 

### If neither works

Use a custom CDC/streaming approach.

```text
Database
   ↓
Custom CDC
   ↓
Staging
   ↓
Auto Loader / Pipeline
   ↓
Bronze
```

This is the highest-effort option.

# 7. C. Cloud Files

If the source is files arriving in cloud storage:

```text
Cloud Storage
      ↓
Auto Loader
      ↓
Bronze
```

**Auto Loader is the default starting point.**

It provides:

* Incremental file ingestion
* Structured Streaming-based processing
* Large-scale file ingestion
* Schema tracking/evolution
* Checkpointing
* Cloud storage integration

The standard Auto Loader pattern uses `cloudFiles` with Spark Structured Streaming. 

---

# 8. Auto Loader Production Concepts

Auto Loader maintains two important locations.

### Schema Location

Stores information about discovered schemas.

```text
_schema/
```

Used to detect schema evolution.

### Checkpoint Location

Stores information about what has already been processed.

```text
_checkpoints/
```

Therefore:

```text
Files
 ↓
Auto Loader
 ├── Schema Location
 └── Checkpoint
 ↓
Bronze
```

Checkpointing allows Auto Loader to process **only new files**, rather than rereading everything. 

---

# 9. Critical Production Rule — Never Delete Checkpoint/Schema Location

This is one of the most important points from the final lecture.

Do **not** casually delete:

```text
_checkpoint
_schema
```

because Auto Loader uses them to remember:

* What files it has processed
* Previous schema information
* Previous streaming progress

Deleting them can reset Auto Loader's state and cause previously processed files to be processed again.

---

# 10. Schema Evolution in Auto Loader

Suppose the original file contains:

```text
order_id
customer_id
amount
```

Later the source adds:

```text
discount_code
```

Auto Loader detects the schema change.

The lecture's behavior is:

```text
New schema detected
       ↓
Schema recorded
       ↓
Current run fails
       ↓
Pipeline retry
       ↓
Retry succeeds
       ↓
New column incorporated
```

This initial failure is expected behavior in the demonstrated setup; the scheduler/job retry handles the restart automatically. 

So:

> **Don't manually babysit the pipeline and restart it after every schema-drift exception.**

Use the job retry mechanism.

---

# 11. Rescued Data

Schema evolution and **bad data** are different situations.

Suppose:

```text
unit_price = "ABC"
```

when the expected value is numeric.

Auto Loader doesn't necessarily fail the whole ingestion.

Instead, the unexpected value can be placed into:

```text
_rescued_data
```

Conceptually:

```text
Source
  ↓
Auto Loader
  ↓
Valid columns + rescued data
  ↓
Bronze
```

The lecture specifically emphasizes monitoring rescued data.

### Important distinction

```text
Schema change
→ can cause a run to fail and then succeed on retry

Bad/incompatible value
→ can be rescued into rescued-data column
```

A non-empty rescued-data field isn't automatically a pipeline failure, but a **growing amount of rescued data is an early warning of source-quality drift**.

---

# 12. Managed Database CDC Monitoring

For managed database CDC:

```text
Database
   ↓
Gateway
   ↓
Staging
   ↓
Pipeline
   ↓
Bronze
```

The **gateway is independent of the ingestion pipeline**.

Therefore, if Bronze suddenly stops receiving new records, check:

1. Gateway health
2. Database connectivity
3. Staging
4. Ingestion pipeline

A quiet/unhealthy gateway can be the first indication that CDC capture has stopped.

# 15. What Every Branch Ultimately Produces

Regardless of the ingestion method:

```text
SaaS ───────────────┐
                    │
Database CDC ───────┤
                    ├──→ Unity Catalog → Bronze
```

The important architectural principle is:

> **Different ingestion mechanisms, same governed Bronze destination.**

That keeps the downstream architecture consistent.

# 16. Production Checklist

### Auto Loader

* ✅ Don't delete checkpoint
* ✅ Don't delete schema location
* ✅ Configure schema evolution appropriately
* ✅ Let Lakeflow Jobs retry failed streams
* ✅ Monitor rescued data

### Managed CDC

* ✅ Monitor gateway health
* ✅ Verify database connectivity
* ✅ Monitor staging
* ✅ Verify connector GA status

### Connector selection

* ✅ Check managed connector availability first
* ✅ Use managed CDC when suitable and GA
* ✅ Use query-based ingestion when CDC isn't available/needed
* ✅ Use Auto Loader for cloud files
* ✅ Use custom CDC only when simpler options don't fit

# 17. Final Mental Model

Remember these **three things**:

### 1. Three connector tiers

```text
Managed → Standard → Community
```

### 2. Three major source shapes

```text
SaaS → Managed Connector

Database → Managed CDC / Query-based / Custom CDC

Cloud Files → Auto Loader
```

### 3. One destination

```text
             ┌── SaaS
             │
             ├── Database
Source ──────┤
             └── Cloud Files
                    ↓
              Lakeflow Connect
                    ↓
             Unity Catalog
                    ↓
                 Bronze
                    ↓
                 Silver
                    ↓
                  Gold
```

**Interview one-liner:**

> **Lakeflow Connect provides managed, standard, and community ingestion options. Choose the connector based on the source: managed connectors for supported SaaS/CDC sources, query-based or custom CDC for databases when managed CDC isn't suitable, and Auto Loader for cloud files. Regardless of the ingestion method, data ultimately lands incrementally into Unity Catalog-governed Bronze tables.**
