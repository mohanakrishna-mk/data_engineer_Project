# Databricks Premium on AWS — Summary in Order

This section explains the **complete process of setting up Databricks Premium on AWS**, including AWS account setup, IAM, billing protection, Databricks subscription, serverless workspace, classic workspace, and cleanup.

The overall goal is:

```text
AWS Account
   ↓
Secure Root User
   ↓
IAM User
   ↓
Billing + Budget Alert
   ↓
AWS Marketplace
   ↓
Databricks Subscription
   ↓
Databricks Account
   ↓
Serverless Workspace
   ↓
Classic Workspace
   ↓
Cleanup Classic Workspace
```

---

# 1. Why Do We Need Databricks Premium?

Most of the course can be practiced using:

```text
Databricks Free Edition
        ↓
Serverless Workspace
```

The lecture estimates that roughly **70–80% of the course** can be practiced this way.

Premium is needed for capabilities that aren't available in Free Edition, especially:

* Classic/Hybrid workspace
* Dedicated compute
* Certain AWS/cloud integrations

So there are two choices:

### Option 1 — Don't create Premium

Use Free Edition and watch the Premium-specific demonstrations.

### Option 2 — Create Premium on AWS

Create an AWS account, subscribe to Databricks and create the required workspaces.

Premium can incur cloud/service costs, so the course emphasizes cost control.

# 3. AWS Root User

The email used to create the AWS account becomes the **root user**.

The root user is the owner of the AWS account.

Important rule:

> Don't use the root user for normal day-to-day AWS work.

Instead:

```text
Root User
   ↓
Secure it
   ↓
Create IAM User
   ↓
Use IAM User for daily work
```

---

# 4. Enable MFA for Root User

The lecture recommends securing the root account using **MFA**.

Flow:

```text
Root User
   ↓
Security Credentials
   ↓
MFA
   ↓
Virtual MFA Device
   ↓
Authenticator App
   ↓
Scan QR
   ↓
Enter MFA Code 1
   ↓
Enter MFA Code 2
   ↓

```

The lecture uses a mobile authenticator application.

So the root account has an additional authentication layer.

---

* Account name

The account ID is also used in IAM-user login URLs.

# 8. Set AWS Region

The lecture recommends using:

* **US East 1 — North Virginia**
* **US East 2 — Ohio**


> Region selection is important because AWS resources are generally created within a specific region.

Also, the region selected while logged in as root does not automatically mean your IAM-user work is using that region, so set it for the IAM user as well.

# 12. Important India Payment Issue Mentioned in the Lecture

The lecture specifically discusses an AWS Marketplace payment problem for **Indian customers** using certain payment methods.

According to the lecture, AWS Marketplace purchases may fail when the account uses:

* UPI
* Indian credit card
* Indian debit card

The lecture attributes this to the billing/entity structure involving **Amazon Internet Services Private Limited (AISPL)** and the Databricks US entity.

The example error shown was essentially:

```text
Invalid payment method
```

This is a lecture-specific/current-at-the-time issue, so don't treat it as a permanent AWS rule.

---

# 13. Workaround: Pay by Invoice

The lecture's workaround is to request AWS support to change the payment instrument to:

```text
Pay by Invoice
```

Process:

```text
Root User
   ↓
AWS Support Center
   ↓
Create Support Case
   ↓
Account / Billing Support
   ↓
Request payment method change
   ↓
Pay by Invoice
```

The support request needs information such as:

* Company/name
* Contact name
* Phone
* Email
* Billing address

After AWS changes the payment method, the Marketplace subscription can be created.

The lecture reports that this process worked for the instructor.

# 21. Classic Workspace — Required Components

The classic workspace requires several AWS resources.

### 1. Workspace S3 Bucket

Used for workspace storage.

```text
Databricks
      ↓
S3 Workspace Storage
```

### 2. Storage Cross-Account IAM Role

Allows Databricks to access the S3 workspace storage.

```text
Databricks
      ↓
Cross-account IAM Role
      ↓
S3
```

### 3. Compute Cross-Account IAM Role

Allows Databricks to create/manage compute resources.

```text
Databricks Control Plane
      ↓
Cross-account IAM Role
      ↓
EC2 / Dedicated Compute
```

# 23. Classic Workspace — Permissions

Two major permission categories:

### Storage permissions

For S3 operations such as:

* Get object
* Put object
* Delete object

### Compute permissions

For EC2-related operations such as:

* Create instances
* Create fleet
* Create launch templates
* Create volumes
* Attach volumes
* Manage instances

So remember:

```text
Storage Role → S3

Compute Role → EC2
```

# 25. Verify Classic Workspace

After deployment, open the workspace.

To confirm it is a **classic workspace**, go to:

```text
Compute
```

```text
All-Purpose Compute

```

---

# 26. Why Classic Workspace Costs Money

This is one of the most important practical points.

Classic workspace creates AWS infrastructure such as:

```text
NAT Gateway
+
Elastic IP
```

These resources can incur charges even when you aren't actively using the workspace.

Therefore:

> Don't leave a classic workspace running when you don't need it.

The lecture gives an approximate example of around **$1/day** for these resources, but actual AWS pricing can vary.

# 27. Classic Workspace Cleanup

Cleanup happens at **two levels**:

```text
1. AWS Account
       ↓
   Delete AWS Resources

2. Databricks Account
       ↓
   Delete Workspace Configurations
```

Both are required.

---

# 28. Step 1 of Cleanup — AWS CloudFormation

The AWS Marketplace deployment creates a **CloudFormation stack**.

Go to:

```text
AWS
 ↓
CloudFormation
 ↓
Stacks
```

You should find the Databricks Marketplace deployment stack.

That stack contains the AWS resources created for the classic workspace.

---

# 29. Inspect CloudFormation Resources

The stack contains resources such as:

* S3 bucket
* Bucket policy
* IAM roles
* Subnets
* NAT Gateway
* Route tables
* VPC
* Internet Gateway
* Security groups
* Elastic IP

The lecture demonstrates approximately **27 resources**.

---

# 30. Empty the S3 Bucket First

Important cleanup issue:

**CloudFormation cannot delete a non-empty S3 bucket.**

So:

```text
S3 Bucket
   ↓
Empty Bucket
   ↓
Delete All Objects
   ↓
CloudFormation Stack Delete
```

If you don't empty it first, stack deletion can fail.

---

# 31. Delete CloudFormation Stack

After emptying the required S3 bucket:

```text
CloudFormation
      ↓
Select Databricks Stack
      ↓
Delete Stack
      ↓
Wait
      ↓
Stack Deleted
```

This removes the AWS infrastructure created by the deployment.

---

# 32. Step 2 of Cleanup — Databricks Account

Deleting the AWS CloudFormation stack does **not** automatically remove the corresponding workspace configuration from the Databricks account.

So go to:

```text
Databricks
    ↓
Manage Account
    ↓
Workspaces
```

The classic workspace may still appear.

Delete it from there.

---

# 33. Delete Classic Workspace

Inside the workspace:

```text
Actions
   ↓
Delete Workspace
   ↓
Confirm
```

After deletion, the classic workspace disappears from the workspace list.

---

# 34. Remove Remaining Databricks Cloud Resources

The lecture then checks:

```text
Cloud Resources
```

and removes the configurations associated with the deleted classic workspace.

Three important configurations are:

```text
Compute Credential
Storage Configuration
Network Configuration
```

Delete them after confirming they're no longer used.

---

# 35. Do NOT Delete the Metastore

The lecture specifically warns about the metastore.

The metastore can be shared by multiple workspaces in the same region.

Example:

```text
                 Metastore
                 /       \
                /         \
      Serverless WS     Classic WS
```

After deleting the classic workspace, the metastore can still be used by the serverless workspace.

Therefore:

> **Do not delete the shared metastore just because you deleted the classic workspace.**

---

# 36. Final Clean State

After cleanup:

```text
AWS
 └── Classic workspace AWS resources → Deleted

Databricks
 ├── Classic workspace → Deleted
 ├── Compute credential → Deleted
 ├── Storage configuration → Deleted
 ├── Network configuration → Deleted
 └── Shared metastore → Retained

Databricks
 └── Serverless workspace → Retained
```

## 🔥 Interview-Level Understanding

The most important concepts from this entire section are:

**AWS account** → provides the cloud infrastructure.

**IAM user** → used for normal AWS administration instead of the root user.

**AWS Marketplace** → where the Databricks SaaS subscription is established.

**Databricks account** → account-level Databricks administration.

**Serverless workspace** → Databricks-managed serverless compute.

**Classic/Hybrid workspace** → supports dedicated compute in the customer's AWS environment.

**Storage cross-account role** → allows Databricks to access customer S3 storage.

**Compute cross-account role** → allows Databricks to manage EC2-based compute.

**CloudFormation** → manages the AWS resources created for the Marketplace deployment.

**Cleanup** → must be done at both the AWS and Databricks levels.

The key architecture is:

```text
                    Databricks
                        │
             ┌──────────┴──────────┐
             │                     │
       Control Plane          Compute
             │              ┌──────┴──────┐
             │              │             │
             │         Serverless      Classic
             │                         Compute
             │                            │
             └────────────────────────────┤
                                          ↓
                                    Customer AWS
                                     ┌────┴────┐
                                     │         │
                                    S3        EC2
                                     │         │
                                Storage Role  Compute Role
```

This section essentially prepares you for the **real AWS + Databricks infrastructure setup** before moving into actual Databricks Data Engineering work.
