# Delta Lake – Complete Lecture Summary

## 1. Introduction to Delta Lake

### Problem with plain Parquet tables

Suppose multiple jobs write Parquet files into the same S3/ADLS directory while users are reading the data.

Three major problems occur:

1. **Atomicity problem**

   * A query may see partially written data.
   * Example: Job A has completed one file but is still writing another file.
   * A reader may see an inconsistent/partial dataset.

2. **No built-in history / rollback**

   * If a bad pipeline overwrites or corrupts data, plain Parquet has no transaction history.
   * Recovery normally requires backups.

3. **Small-file performance problem**

   * Every small batch can create another Parquet file.
   * Thousands of small files make Spark scans slow.

Delta Lake was designed to address these problems. 

### What is Delta Lake?

Delta Lake is a **storage/transaction layer on top of cloud storage**.

It is:

```text
S3 / ADLS
   +
Delta Lake
```

It is **not a replacement for S3/ADLS** and is not itself a traditional database.

A Delta table mainly contains:

```text
Delta Table
│
├── Parquet data files
│
└── _delta_log/
      ├── 000000.json
      ├── 000001.json
      ├── 000002.json
      └── ...
```

The transaction log records:

* Added files
* Removed files
* Table changes
* Transaction/version information
* File statistics

This transaction log is what provides Delta's important capabilities. 

### Delta + Unity Catalog architecture

Think of Databricks as:

```text
Unity Catalog
   ↑
Governance / metadata
   ↑
Delta Lake
   ↑
Parquet + transaction log
   ↑
S3 / ADLS
```

Unity Catalog handles things such as:

* Table metadata
* Table names
* Permissions
* Governance

Delta Lake handles:

* Transactions
* Versioning
* Table format
* Data-file management

# 2. Creating and Managing Delta Tables

The lecture covers **three ways to create Delta tables**. 

## Approach 1 — CREATE TABLE

```sql
CREATE OR REPLACE TABLE products (
    product_id INT,
    name STRING,
    category STRING,
    price DOUBLE
)
USING DELTA;
```

Then:

```sql
INSERT INTO products VALUES (...);
```

`CREATE OR REPLACE TABLE` is useful when the table may already exist.

---

## Approach 2 — CTAS

CTAS = **Create Table As Select**

```sql
CREATE OR REPLACE TABLE electronics
USING DELTA
AS
SELECT product_id, name, price
FROM products
WHERE category = 'electronics';
```

Here:

* Schema is inferred from the SELECT.
* Columns/data types come from the query result.
* Data is created at the same time.

---

## Approach 3 — Spark DataFrame API

```python
df.write \
  .format("delta") \
  .mode("append") \
  .saveAsTable("catalog.schema.table")
```

The DataFrame schema can be used to create the table.

---

## Managed vs External Delta Tables

### Managed table

Databricks manages:

```text
Metadata + Data
```

Databricks determines the storage location.

Dropping a managed table eventually removes its data as well.

### External table

Databricks manages:

```text
Metadata only
```

You explicitly provide the storage location.

```sql
CREATE TABLE products_ext
USING DELTA
LOCATION 's3://my-bucket/products/';
```

Dropping it removes the Unity Catalog metadata but does **not** delete the underlying data.

### Remember

```text
Managed  → Databricks owns metadata + data
External → Databricks owns metadata, you own data
```

# 3. Reading and Writing Delta Tables

Delta supports both **batch and streaming** workloads. 

## Batch write

Start with a DataFrame:

```python
df.write \
  .format("delta") \
  .mode("append") \
  .saveAsTable("events")
```

### Append

```text
Existing data
     +
New records
     ↓
Delta table
```

If the table doesn't exist, it can be created.

---

## Overwrite

```python
df.write \
  .format("delta") \
  .mode("overwrite") \
  .saveAsTable("events")
```

Important point:

**Overwrite is an atomic transaction.**

Readers don't see:

```text
DELETE old data
        ↓
empty table
        ↓
WRITE new data
```

Instead they see either:

```text
Old version
     OR
New version
```

The transaction log commits the new state atomically. 

---

## Delta History

You can inspect table history:

```sql
DESCRIBE HISTORY events;
```

Every transaction creates a new Delta version.

Example:

```text
Version 0 → table creation
Version 1 → insert
Version 2 → overwrite
Version 3 → optimize
```

---

## Streaming write

Delta can also be the destination for Structured Streaming.

Conceptually:

```text
Streaming source
      ↓
Spark Structured Streaming
      ↓
Delta table
```

A Delta table can simultaneously support:

```text
Batch writer
Streaming writer
Batch reader
Streaming reader
```

without application-level coordination. 

This is one of the important reasons Delta is called a **unified table format**.

---

# 4. Time Travel

Delta maintains table history through the transaction log.

Each version represents a point on the table's timeline. 

You can query an older version using:

### Version-based

```sql
SELECT *
FROM employees VERSION AS OF 5;
```

### Timestamp-based

```sql
SELECT *
FROM employees
TIMESTAMP AS OF '2026-05-28 13:24:27';
```

### Important

Delta does **not** store a complete copy of the table for every version.

Instead:

```text
Transaction Log
      ↓
Which files belonged to version X?
      ↓
Read those Parquet files
```

### Uses

Time travel is useful for:

* Auditing
* Debugging
* Point-in-time reporting
* Investigating data changes
* Recovery/rollback workflows

### Limitation

Time travel only works while the required historical Parquet files still exist.

Once old files are physically removed by maintenance such as `VACUUM`, those versions may no longer be queryable. 

---

# 5. OPTIMIZE and VACUUM

This lecture addresses the **small-file problem**.

Suppose streaming/incremental jobs continuously write tiny batches:

```text
Write 1 → file1
Write 2 → file2
Write 3 → file3
...
Write 10000 → file10000
```

Thousands of small files can hurt query performance. 

## OPTIMIZE

```sql
OPTIMIZE transactions;
```

Conceptually:

```text
Before:

file1
file2
file3
file4
...
file1000

        OPTIMIZE

After:

larger files
```

It **compacts small Parquet files into larger files**.

Important:

> OPTIMIZE improves file layout but does not physically delete the old files immediately.

---

## VACUUM

VACUUM physically removes old files that are no longer required within the configured retention window.

Conceptually:

```text
OPTIMIZE
   ↓
new optimized files
   ↓
old files remain temporarily
   ↓
VACUUM
   ↓
old unused files physically deleted
```

### Difference

| OPTIMIZE                              | VACUUM                               |
| ------------------------------------- | ------------------------------------ |
| Compacts files                        | Deletes old files                    |
| Improves query performance            | Reduces storage                      |
| Does not immediately remove old files | Physically removes files             |
| Helps small-file problem              | Affects historical-file availability |

The lecture emphasizes that the retention window controls how far back time travel can go. 

---

# 6. RESTORE / Rollback

Suppose a production table has:

```text
Version 0
Version 1
Version 2
Version 3  ← valid
Version 4  ← bad update
Version 5  ← bad delete
```

You can inspect history:

```sql
DESCRIBE HISTORY employees;
```

Then restore:

```sql
RESTORE TABLE employees TO VERSION AS OF 3;
```

Or restore using a timestamp.

The important point is that **restore itself creates a new version**.

Example:

```text
Version 5 → corrupted
       ↓
RESTORE TO VERSION 3
       ↓
Version 6 → restored state
```

The old versions aren't erased from the Delta history. 

---

## Full vs selective rollback

### Full table rollback

Use:

```sql
RESTORE TABLE ...
```

when the entire table needs to return to a previous valid state.

### Selective rollback

If only a subset of records is corrupted:

```text
Time Travel
     ↓
Read correct records from old version
     ↓
MERGE
     ↓
Restore only affected records
```

This avoids rolling back the entire large table. 

---

# 7. MERGE

`MERGE` is one of the most important Delta operations.

It allows:

```text
UPDATE
INSERT
DELETE
```

as part of a single atomic operation. 

There are two sides:

```text
Source
  ↓
MERGE
  ↓
Target Delta table
```

Basic structure:

```sql
MERGE INTO target t
USING source s
ON t.id = s.id

WHEN MATCHED THEN
    UPDATE SET ...

WHEN NOT MATCHED THEN
    INSERT (...);
```

### Matched

Record exists in both:

```text
Source ID 2
Target ID 2
      ↓
UPDATE
```

### Not matched

Record exists only in source:

```text
Source ID 6
Target doesn't have ID 6
      ↓
INSERT
```

### Full synchronization

For a full source snapshot, you can also handle deletes:

```text
Source has record
Target has record
     → update

Source has new record
     → insert

Target has record
Source doesn't have it
     → delete
```

The lecture also covers:

* Late-arriving records
* Comparing source/target timestamps
* Full synchronization
* CDC
* Conditional updates
* Deletes



### Important MERGE warning

The merge condition should use a reliable unique key.

For example:

```sql
ON target.customer_id = source.customer_id
```

The key should ideally:

* Be unique
* Not contain NULLs
* Correctly identify one target record

Otherwise merge can produce incorrect results. 

### Performance consideration

A merge can require scanning the target to find matching records.

For a huge target table, this can become expensive.

Therefore, the merge condition and table layout/optimization are important.

# 8. DELETE, UPDATE and Idempotence

## DELETE

Normal SQL works:

```sql
DELETE FROM customers
WHERE customer_id IN (...);
```

Historically, Delta could implement modifications using **copy-on-write**:

```text
Old Parquet file
      ↓
Remove deleted records
      ↓
Write new Parquet file
```

The lecture then explains **Deletion Vectors**.

Instead of immediately rewriting the entire Parquet file, Delta can record deleted rows in a deletion vector.

```text
Parquet file
    +
Deletion Vector
    ↓
Reader skips deleted records
```



---

## UPDATE

Example:

```sql
UPDATE customers
SET tier = 'platinum'
WHERE customer_id IN (...);
```

Delta similarly tracks modifications using its transaction/data-management mechanisms.

---

## Idempotence

Real pipelines can execute more than once because of:

* Job retries
* Spark task speculation
* At-least-once systems such as Kafka/Kinesis
* Manual reruns

Without proper design:

```text
Run 1 → records inserted
Run 2 → same records inserted again
                     ↓
                 duplicates
```

An idempotent pipeline produces the **same final state even when the operation is retried**.

A common Delta approach is to use deterministic keys and `MERGE` rather than blindly appending the same data.

# 9. Schema Enforcement and Schema Evolution

## Schema Enforcement

Delta protects the table schema by default. 

Suppose table schema is:

```text
product_id INT
name       STRING
price      DOUBLE
```

Incoming data has:

```text
product_id
name
price
discount_percentage   ← new column
```

By default, Delta rejects the write.

Similarly:

```text
price = STRING
```

when the table expects:

```text
price = DOUBLE
```

will also be rejected.

### Schema enforcement protects:

```text
Column names
+
Column data types
```

---

## Schema Evolution

Sometimes schema changes are legitimate.

Example:

```text
Old:
id
name
price

New:
id
name
price
discount
```

### Option 1 — mergeSchema

Per-write option:

```python
df.write \
  .format("delta") \
  .option("mergeSchema", "true") \
  .mode("append") \
  .saveAsTable("products")
```

Only that write allows schema evolution.

This is explicit and controlled. 

### Option 2 — autoMerge

Session-level:

```python
spark.conf.set(
    "spark.databricks.delta.schema.autoMerge.enabled",
    "true"
)
```

This affects Delta writes in the session.

The lecture presents `mergeSchema` as the more explicit approach for production.

### Existing rows

When a new column is added:

```text
Old rows → NULL
New rows → actual value
```

No existing data is deleted.

# 10. Type Widening and VARIANT

## Type Widening

Normally, changing:

```text
INT → LONG
```

is not automatically allowed.

Type widening allows certain safe promotions without rewriting all existing Parquet data.

Examples:

```text
BYTE → SHORT → INT → LONG

FLOAT → DOUBLE

DATE → TIMESTAMP
```



You first enable the table capability, then can alter the column or use schema merge.

Conceptually:

```text
INT
 ↓
LONG
```

The metadata/schema changes without rewriting the entire historical dataset.

### Important limitation

Type widening works **within compatible type families**.

For example:

```text
INT → LONG        ✅
FLOAT → DOUBLE    ✅
DATE → TIMESTAMP  ✅

LONG → DOUBLE     ❌
```

For incompatible changes, the lecture says the table needs to be rewritten. 

---

## VARIANT

VARIANT is useful for **semi-structured/JSON data whose structure can vary**.

Three approaches for JSON:

### String

```text
JSON → STRING
```

Pros:

* Very flexible
* Any JSON structure can be stored

Cons:

* JSON must be parsed during queries
* Can become expensive at large scale

### Struct

```text
JSON → STRUCT
```

Pros:

* Typed fields
* Better query performance/pruning

Cons:

* Schema is more rigid

### Variant

```text
JSON → VARIANT
```

Useful when:

* JSON schema changes
* Different records have different fields
* External systems control the JSON structure

The lecture demonstrates querying Variant paths and casting values when needed. 

Conceptually:

```sql
payload:unit
```

and cast when comparing:

```sql
payload:unit::string
```

Missing JSON paths return `NULL`.

# 11. Constraints and Identity Columns

The final lecture adds **data-quality rules at the table level**.

Schema enforcement protects the **structure**.

Constraints protect **business/value rules**. 

## NOT NULL

Example:

```sql
customer_id INT NOT NULL
```

Then:

```text
customer_id = NULL
        ↓
WRITE FAILS
```

---

## CHECK constraint

Example:

```sql
ALTER TABLE orders
ADD CONSTRAINT valid_amount
CHECK (amount > 0);
```

Then:

```text
amount = 100  → ✅
amount = -10  → ❌
```

Can also have more complex conditions:

```sql
CHECK (status IN ('pending', 'processing', 'completed', 'cancelled'))
```

Always give constraints meaningful names because the name appears in error messages.

Constraints can be inspected with:

```sql
SHOW TABLE PROPERTIES orders;
```

They apply to **new writes**; existing rows are not retroactively validated. 

---

# Identity Columns

Useful especially for **surrogate keys** in dimension tables.

## GENERATED ALWAYS AS IDENTITY

Databricks generates the value.

```text
Insert row
   ↓
ID automatically generated
```

You cannot provide your own value.

Example:

```text
1
2
3
4
...
```

---

## GENERATED BY DEFAULT AS IDENTITY

You can either:

```text
Provide ID → use provided ID
```

or:

```text
Don't provide ID → generate ID
```

This is useful when migrating existing systems where some surrogate keys already exist.

Important:

> Identity values are unique, but gaps can occur. Continuous numbering is not guaranteed.
