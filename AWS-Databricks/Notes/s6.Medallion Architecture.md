## Medallion Architecture — Ordered Summary

### 1. Why do we need Medallion Architecture?

A common data engineering problem is **multiple pipelines reading the same raw data and applying overlapping logic**.

Example:

```text
Same Raw Source
     ↓
Pipeline 1 → Table A
Pipeline 2 → Table B
Pipeline 3 → Table C
```

This creates:

* Duplicate transformation logic
* Different results for the same source
* Difficult debugging
* Schema changes breaking multiple pipelines
* No clear separation between raw data, business logic, and consumption

This situation is referred to in the lecture as a **data swamp**.

The solution is to introduce clear data layers:

```text
Bronze → Silver → Gold
```

Each layer has **one responsibility and a clear contract**. 

---

# 2. Three Layers

### Bronze — Raw

Purpose:

> **Preserve what arrived.**

* Raw data
* No transformation
* No filtering
* No typecasting
* No business logic
* Add ingestion/source metadata
* Can contain duplicates
* Can contain nulls/bad data
* Acts as an audit/replay layer
* Usually append-only

```text
Source
  ↓
Bronze
```

If Silver has a bug, we can rebuild Silver from Bronze without going back to the source.

---

### Silver — Clean/Validated

Purpose:

> **Make the data correct and enforce quality contracts.**

Typical operations:

* Type casting
* Deduplication
* Null validation
* Data quality rules
* Schema enforcement
* Joining reference data
* Derived reusable fields

Silver should contain data that downstream consumers can trust.

```text
Bronze
   ↓
Silver
```

The lecture describes Silver as the layer where records are cleaned, typed, deduplicated and validated. 

---

### Gold — Business/Consumption

Purpose:

> **Answer specific business questions efficiently.**

Examples:

* Daily revenue
* Customer lifetime value
* Product performance
* Management dashboards
* BI reports

Gold is:

* Pre-aggregated
* Read-optimized
* Designed for specific consumers
* Usually faster to query

```text
Silver
   ↓
Gold
```

Overall:

```text
Source
  ↓
Bronze
  ↓
Silver
  ↓
Gold
  ↓
BI / Dashboards / Business
```

**Direction is one-way.**

```text
Bronze → Silver → Gold
```

Data should not flow backward.

---

# 3. Important Medallion Rules

### Rule 1 — Bronze must preserve everything

Don't do:

```text
Source → Filter → Bronze
```

Instead:

```text
Source → Bronze
```

If the source sends bad data, **Bronze keeps it**.

---

### Rule 2 — Don't put business logic in Bronze

For example:

```text
Only orders from last 90 days
```

shouldn't be implemented in Bronze.

Otherwise, older data is permanently lost from the Medallion pipeline.

---

### Rule 3 — Don't skip Silver

Avoid:

```text
Bronze → Gold
```

Prefer:

```text
Bronze → Silver → Gold
```

Silver provides the clean, validated data needed to explain how Gold numbers were produced.

---

### Rule 4 — Gold is not the ultimate source of truth

Gold is a **materialization of Silver**.

If Silver logic changes:

```text
Bronze
   ↓
Silver changes
   ↓
Gold must be rebuilt
```

---

# 4. Bronze Implementation

The lecture then implements a small end-to-end example.

Two source datasets are created:

```text
Orders
Customers
```

Instead of reading actual S3 files, CSV strings are used to simulate files arriving into S3.

The source data intentionally contains duplicates.

For example:

```text
Order 1001
Order 1001
```

The important point is:

> Duplicates are acceptable in Bronze.

Everything is initially treated as a **string**.

Why?

Because Bronze should not reject data simply because its value doesn't match an expected type.

---

# 5. Bronze Metadata

The source data is enriched with pipeline metadata.

At minimum:

```text
_ingest_timestamp
_source
_source_file
```

The underscore convention indicates that these fields were generated by the pipeline rather than coming from the source.

Example:

```text
Orders source
      ↓
Add metadata
      ↓
Bronze Orders
```

---

# 6. Writing Bronze Tables

The example creates:

```text
bronze_orders
bronze_customers
```

using Delta format.

For the demonstration:

```text
mode = overwrite
```

is used so the notebook can be repeatedly executed.

But in production:

```text
Bronze → append
```

is normally used because Bronze continuously absorbs incoming records.

The resulting Bronze tables contain:

* All source records
* Duplicates
* String data types
* Metadata columns

The lecture verifies that all 9 order rows and all 5 customer rows were preserved.

---

# 7. Silver Layer — Purpose

Silver's job is to enforce a **data-quality contract**.

```text
Bronze
  ↓
Clean
  ↓
Validate
  ↓
Deduplicate
  ↓
Typecast
  ↓
Silver
```

Important Silver operations:

1. Deduplication
2. Type enforcement
3. Null validation
4. Derived fields
5. Other data-quality rules

The lecture emphasizes that bad Silver doesn't necessarily cause a pipeline failure; it can instead result in **incorrect dashboard numbers**. 

---

# 8. Silver — Orders

First, duplicates are identified.

`order_id` is treated as the primary key.

Example:

```text
order_id
--------
101
101  ← duplicate
```

### Deduplication technique

The lecture uses:

```text
ROW_NUMBER()
OVER (
    PARTITION BY order_id
    ORDER BY _ingest_timestamp DESC
)
```

Then:

```text
RN = 1
```

is retained.

So if we have:

```text
101 → older
101 → newer
```

we keep:

```text
101 → newer
```

This avoids random duplicate selection.

---

# 9. Silver — Null Validation

Critical fields are checked:

```text
order_id
customer_id
quantity
unit_price
```

If any of these are NULL:

```text
Bronze → keep
Silver → reject
```

This is important:

> The invalid record is not deleted from Bronze.

Bronze remains the original audit trail.

---

# 10. Silver — Type Casting

Bronze contains strings.

Silver converts them to appropriate types.

Example:

```text
order_id      → INT
customer_id   → STRING
product_id    → STRING
quantity      → INT
unit_price    → DOUBLE/DECIMAL
order_date    → DATE
status        → STRING
```

---

# 11. Silver — Derived Field

The lecture creates:

```text
order_total
```

using:

```text
quantity × unit_price
```

Example:

```text
quantity = 3
unit_price = 100

order_total = 3 × 100
             = 300
```

This avoids every Gold query repeatedly calculating the same reusable value.

---

# 12. Silver Orders Result

After processing:

```text
Bronze Orders = 9 rows
Duplicate removed = 1
Silver Orders = 8 rows
```

Silver now has:

* Correct data types
* No duplicate order IDs
* No critical NULLs
* Derived `order_total`

---

# 13. Silver — Customers

The same approach is applied to customers.

Rules:

```text
customer_id IS NOT NULL
email IS NOT NULL
```

Duplicates are handled using:

```text
ROW_NUMBER()
OVER (
    PARTITION BY customer_id
    ORDER BY _ingest_timestamp DESC
)
```

Keep only:

```text
RN = 1
```

`signup_date` is converted to:

```text
DATE
```

Other fields remain strings where appropriate.

Result:

```text
Bronze Customers = 5
Duplicate removed = 1
Silver Customers = 4
```

---

# 14. Initial Silver Load

The first implementation is a **full refresh**:

```text
Bronze
  ↓
Read entire Bronze
  ↓
Transform
  ↓
Drop/Recreate Silver
```

Conceptually:

```text
Every run
    ↓
Read all Bronze
    ↓
Rebuild Silver
```

This is fine for demonstrating the architecture, but production pipelines normally use incremental processing.

---

# 15. Incremental Silver Load

The production-oriented approach is:

> **Incremental Silver + MERGE**

Goal:

```text
Run multiple times
        ↓
No duplicate creation
        ↓
Idempotent result
```

---

# 16. How Incremental Processing Works

Bronze contains:

```text
_ingest_timestamp
```

Silver already contains previously processed data.

Find:

```text
MAX(_ingest_timestamp)
```

from Silver.

Then process only Bronze records newer than that timestamp.

Example:

```text
Silver processed until:
15 Jan 23:59

New Bronze records:
16 Jan onward
```

Process only:

```text
16 Jan onward
```

instead of scanning the entire Bronze table.

---

# 17. Incremental Silver Flow

```text
Bronze
  │
  ├── _ingest_timestamp > MAX(Silver timestamp)
  │
  ↓
New records only
  ↓
Deduplicate
  ↓
Type cast
  ↓
MERGE
  ↓
Silver
```

The lecture's incremental query also:

* Removes records with NULL order IDs
* Deduplicates using `ROW_NUMBER`
* Performs type casting

---

# 18. MERGE Logic

The transformed incremental data becomes the source for:

```text
MERGE INTO silver
```

Match using:

```text
source.order_id = target.order_id
```

### When matched

```text
UPDATE
```

### When not matched

```text
INSERT
```

Conceptually:

```text
             ┌── matched ──→ UPDATE
Source ──────┤
             └── new ──────→ INSERT
```

This makes the Silver pipeline **idempotent**.

---

# 19. Gold Layer

Gold answers:

> **A specific business question for a specific consumer.**

Unlike Bronze/Silver:

```text
Bronze → preservation
Silver → correctness
Gold   → usability + speed
```

Gold is generally:

* Aggregated
* Read-optimized
* Consumer-specific

---

# 20. Gold Example — Daily Revenue by Customer Tier

Business requirement:

> Calculate daily revenue by customer tier.

Customer tiers:

```text
Gold
Silver
Bronze
```

Business rule:

> **Only completed orders count as revenue.**

Therefore:

```text
status = 'completed'
```

Orders that are:

```text
pending
cancelled
```

are excluded from this Gold metric.

Importantly, this filter is **not applied in Silver**. Silver retains valid orders regardless of whether they are completed.

---

# 21. Gold Query Flow

```text
Silver Orders
      +
Silver Customers
      ↓
Join on customer_id
      ↓
Filter completed orders
      ↓
Group by:
    order_date
    customer_tier
      ↓
Aggregate
      ↓
Gold Daily Revenue
```

Metrics include:

* Order count
* Unique customer count
* Total revenue
* Average order value
* Refresh timestamp

---

# 22. Materialized Gold Table vs View

Two options are discussed.

### Materialized table

Stores the actual result.

```text
Silver
  ↓
Query
  ↓
Gold Table
  ↓
Consumer
```

Use it when:

* Query frequency is high
* Underlying joins are expensive
* Performance is important

---

### View

Stores the query rather than the result.

```text
Silver
  ↓
Gold View
  ↓
Consumer
```

Use it when:

* Query frequency is low
* Silver query is fast enough
* Freshness is more important than query performance

The example creates both:

```text
gold_daily_revenue
gold_daily_revenue_view
```

The materialized table contains a refresh timestamp; the view does not because it evaluates the query when accessed.

---

# 23. Medallion Decision Tree

### When should you add a layer?

Add a layer when:

> Transformation logic or audience is different enough that mixing them creates confusion or coupling.

### Bronze → Silver?

Almost always.

Because:

```text
Raw ≠ Clean
```

### Silver → Gold?

Depends on the use case.

One consumer:

```text
Silver
  ↓
View
```

Many consumers:

```text
Silver
  ↓
Multiple Gold tables/views
```

---

# 24. When Should You Collapse Layers?

The lecture strongly recommends **not collapsing layers in production**.

Avoid:

```text
Bronze → Gold
```

because when bad source data causes incorrect Gold numbers, there is no clean Silver layer to help debug and correct the problem.

---

# 25. What Goes Where?

A very useful interview rule:

| Logic                         | Layer  |
| ----------------------------- | ------ |
| Preserve raw data             | Bronze |
| Add ingestion metadata        | Bronze |
| Type casting                  | Silver |
| Deduplication                 | Silver |
| Null/data-quality validation  | Silver |
| Reusable derived fields       | Silver |
| Reference-data joins          | Silver |
| Specific business question    | Gold   |
| Business-specific aggregation | Gold   |
| Dashboard-specific output     | Gold   |

The simplest rule:

> **Correctness → Silver**
> **Specific business question → Gold**

---

# 26. How Many Gold Tables?

Don't create Gold tables for every request automatically.

Create them for:

> **Distinct business questions.**

Too many Gold tables create:

```text
Gold Table Sprawl
```

For example:

```text
47 Gold tables
      ↓
Different teams
      ↓
Slightly different definitions
      ↓
Nobody knows which metric is authoritative
```

Use governance to control this.

Unity Catalog can help with:

* Ownership
* Descriptions
* Permissions
* Canonical business tables

---

# 27. Medallion Anti-Patterns

### Anti-pattern 1 — Business logic in Bronze

Bad:

```text
Bronze → only last 90 days
```

Problem:

Historical data disappears.

Correct:

```text
Bronze → complete history
Silver/Gold → apply filters
```

---

### Anti-pattern 2 — Silver as temporary staging

Bad:

```text
Bronze → Silver → Gold
           ↓
         DELETE
```

Silver should be **persistent**.

If Gold needs rebuilding:

```text
Silver → rebuild Gold
```

not:

```text
Bronze → rebuild everything
```

---

### Anti-pattern 3 — Gold table sprawl

Too many slightly different Gold tables cause inconsistent business metrics.

Solution:

```text
Governance
   ↓
Canonical metrics
   ↓
Controlled Gold layer
```

---

### Anti-pattern 4 — Undocumented layer contracts

Every Silver table should document:

> What quality standard does this table enforce?

Every Gold table should document:

> What business question does this table answer and what filters/business rules does it apply?

The lecture suggests documenting this through **Unity Catalog table comments**.

---

# 28. Final Medallion Architecture

```text
                 SOURCE SYSTEMS
                       │
                       ▼
              ┌─────────────────┐
              │     BRONZE      │
              │                 │
              │ Raw             │
              │ Append-only     │
              │ Metadata        │
              │ Full history    │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │     SILVER      │
              │                 │
              │ Clean           │
              │ Typed           │
              │ Deduplicated    │
              │ Validated       │
              │ Reusable logic  │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │      GOLD       │
              │                 │
              │ Business metrics│
              │ Aggregations     │
              │ Read optimized  │
              │ Consumer-specific│
              └────────┬────────┘
                       │
                       ▼
              BI / Dashboards /
              Business Users
```

### Final mental model

**Bronze = What did the source send?**

**Silver = Is the data correct and usable?**

**Gold = What business question are we answering?**

And the dependency is always:

```text
Bronze → Silver → Gold
```

This becomes the **skeleton for the rest of the Databricks data engineering pipeline**: business requirements determine the rules, while tools and automation can change around this basic architecture.
