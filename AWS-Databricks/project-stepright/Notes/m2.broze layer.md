# Bronze Layer — Complete Summary

## Part 1: Bronze CDC Ingestion

The goal is to move the **3 CDC sources** from the landing zone into Bronze:

1. Orders
2. Order Items
3. Customers

The main principle is:

> **Bronze keeps the data exactly as it arrived from Debezium.**

So we do **not** extract only the `after` fields in Bronze. We preserve the complete CDC envelope:

```text
OP
TSMS
before
after
```

This allows the data to be replayed and gives Silver everything it needs later.

# 3. Define schemas manually

The project **does not allow Auto Loader to infer the CDC schema**.

Why?

Because the schema is already known and documented.

So schemas are explicitly defined for:

```text
orders
order_items
customers
```

Each CDC record has this structure:

```text
CDC Envelope
├── OP
├── TSMS
├── before
└── after
```

And `before` and `after` contain the actual business record.

For example:

```text
after
├── order_id
├── customer_id
├── order_status
├── order_date
└── ...
```

A reusable `envelope_schema()` function wraps the business row schema inside:

```text
OP + TSMS + before + after
```

This avoids defining the same business schema twice for `before` and `after`.

## Design decisions

### Decision 1 — Use Auto Loader for all files

Even though:

```text
Products → changes rarely
Clickstream → changes continuously
```

both use the same Auto Loader pattern.

Why?

Because the fundamental problem is the same:

> Detect and process new files reliably.

---

### Decision 2 — Explicit schemas

Just like CDC sources, the file schemas are already known.

Therefore:

```text
No schema inference
```

Schemas are explicitly defined for:

```text
categories
products
inventory
clickstream
```

---

### Decision 3 — No CDC envelope

File-based sources are **not CDC events**.

Therefore they don't need:

```text
OP
TSMS
before
after
```

Instead:

```text
Raw file columns
+
ingested_at
+
_source_file
```

That's it.

# 11. Important Bronze Principle

Remember this for interviews:

> **Bronze = raw and replayable, not cleaned.**

Therefore Bronze:

* Doesn't reject bad records.
* Doesn't perform business validation.
* Doesn't deduplicate.
* Doesn't enforce business rules.
* Preserves the source structure.
* Adds ingestion metadata.

The next layer is responsible for quality and business transformations.

# 12. What happens next — Bronze Data Quality

The next lecture introduces a layer **between Bronze and Silver**.

Instead of modifying Bronze:

```text
Bronze
  ↓
Quality Check
  ↓
Valid / Quarantine
  ↓
Silver
```

A bad record isn't:

❌ rejected
❌ silently deleted
❌ manually edited

Instead:

```text
Bronze record
      ↓
Quality rules
      ↓
 ┌────┴─────┐
 ▼          ▼
Valid    Quarantine
```

The original Bronze data remains untouched. 

### Final structure

```text
Bronze
   │
   ▼
Bronze Quality
   │
   ├── Valid ───────→ Silver
   │
   └── Quarantine ──→ Monitoring / Alerts
```

And if a quarantined record needs correction, it **comes back through the normal source/ingestion path as new data** rather than someone manually editing the Bronze record. 

### One-line flow to remember

```text
Landing → Auto Loader → Bronze (7 tables) → Quality Check → Valid/Quarantine → Silver
```

Yes 👍 This looks like the **missing implementation lecture** for the Bronze Quarantine/Data Quality layer. It continues directly from the previous lecture.

The order is:

**Bronze raw tables → Quality check → Valid + Quarantined tables → Silver/Monitoring**

### What this lecture adds

1. Create `bronze_quality.py` inside the ingestion pipeline.
2. Define data-quality rules for each of the **7 Bronze tables**.
3. For each Bronze table:

   * Read the Bronze table.
   * Apply `expect_all` rules.
   * **Do not drop/fail records** when rules fail.
   * Add `isQuarantined = true/false`.
4. Create a **private intermediate streaming table**.
5. From that intermediate table create:

   * `<table>_valid`
   * `<table>_quarantined`
6. Silver reads only the **valid** tables.
7. Monitoring/investigation reads the **quarantined** tables.
8. Original Bronze tables remain unchanged. 

### Example — Orders

Rules:

```text
valid_order_id
    → after.orderId IS NOT NULL

valid_customer_reference
    → after.customerId IS NOT NULL

valid_total_amount
    → after.totalAmount IS NULL
      OR after.totalAmount >= 0
```

These rules are evaluated without rejecting the source record. 

Then:

```text
bronze_orders
       ↓
private intermediate table
       ↓
   isQuarantined
      /       \
   false       true
     ↓           ↓
orders_valid   orders_quarantined
```

The intermediate table is private and partitioned by `isQuarantined`. 

### Important point

The lecture explicitly says **do not fix quarantined records directly**.

If a bad source record is corrected, the correction should come through the normal source → ingestion → pipeline flow as new/update data. This preserves the history/audit trail of what was wrong and how it was corrected. 

### Final Bronze state

```text
                 ┌── Valid tables ─────→ Silver
7 Bronze tables ─┤
                 └── Quarantined tables → Monitoring
                       ↑
                 Private quality tables
```

So yes — **this was the missing part**, and it completes the Bronze layer implementation after the previous lecture's design discussion. The pipeline ends up with **7 raw Bronze + 7 valid + 7 quarantined**, while the 7 intermediate quality tables remain private.
