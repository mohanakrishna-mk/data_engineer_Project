## StepRite Lakehouse — Explanation Summary

This section is mainly about **setting up the project foundation and preparing development data** before building the actual Bronze/Silver/Gold pipelines.

### 1. Connect GitHub to Databricks first

The first decision is:

```text
GitHub Repository
       ↕
Databricks Git Folder
```

Create the GitHub repository:

```text
step-right-lakehouse
```

Then connect it to Databricks using a **Git Folder**.

The reason is simple: any notebooks/code created inside the Git Folder can be committed and pushed directly to GitHub. 

For authentication, the lecture uses a **GitHub Personal Access Token (PAT)** with:

* `repo`
* `workflow`

---

# 2. Create a dedicated schema

Instead of putting StepRite tables into an existing schema:

```text
dev.dbx_course
```

the project creates:

```text
dev.step_right
```

So the structure becomes:

```text
dev
└── step_right
    ├── tables
    └── volumes
```

This keeps the project isolated and easy to identify.

---

# 3. Create one landing volume

Instead of creating a separate volume for every source, use **one landing volume**:

```text
dev.step_right.landing
```

Inside it:

```text
landing/
├── orders/
├── order_items/
├── customers/
├── products/
├── categories/
├── clickstream/
└── inventory/
```

So the idea is:

> **One volume = one landing zone; subfolders = different sources.**

This gives a simpler permission and management model.

### Why `.gitkeep`?

Git doesn't track empty folders.

So `.gitkeep` files are temporarily placed inside empty directories:

```text
tests/
└── .gitkeep
```

This allows the entire project skeleton to be committed to GitHub.

# 6. Why do we need a data generator?

The actual company source systems aren't available for the course.

Using real customer/order data isn't appropriate because of **data privacy**.

Therefore, create:

```text
data_generator.py
```

It uses the **Faker** Python library to generate realistic development/test data.

Important point:

> `data_generator.py` is a normal Python script, **not a Databricks notebook**.

Why?

Because it represents external systems such as:

* Order system
* Customer system
* Warehouse system
* Product system

Those systems exist outside Databricks in the real architecture.

---

# 7. What does the data generator create?

For **Batch 0**, it creates the initial complete snapshot:

| Dataset     | Approx. records |
| ----------- | --------------: |
| Customers   |           5,000 |
| Orders      |          20,000 |
| Order items |         38,000+ |
| Products    |             500 |
| Categories  |               6 |
| Clickstream |        ~180,000 |
| Inventory   |          45,000 |

The generated data maintains the relationships between the datasets.

For example:

```text
Customer
   ↓
Order
   ↓
Order Item
   ↓
Product
```

---

# 8. Batch concept is important

The generator doesn't generate data only once.

It works with batches:

```text
Batch 0 → Initial snapshot
Batch 1 → New/updated data
Batch 2 → More changes
...
```

### Batch 0

Represents:

> "This is the complete state of StepRite when the pipeline starts."

### Future batches

Will simulate things such as:

```text
New customer
New order
Order status update
Customer loyalty update
```

This is important later for testing:

* CDC
* SCD Type 2
* Incremental processing

---

# 9. `generator_state.json`

The generator creates:

```text
generator_state.json
```

This stores information about previously generated IDs/data.

For example:

```text
Existing customers
Existing orders
Existing products
```

Then Batch 1 can know which existing records it should reference or update.

**Important:** this state file stays on the local machine and isn't pushed to GitHub.

---

# 10. Why staging volume?

The generated data initially exists on your laptop:

```text
Laptop
   ↓
data_generator.py
   ↓
raw_sources/batch_0
```

But Databricks cannot simply treat your laptop folder as the production landing zone.

So they introduce an intermediate **staging volume**:

```text
dev.step_right.staging
```

Flow:

```text
Local Laptop
     ↓
data_generator.py
     ↓
batch_0
     ↓
Databricks staging volume
     ↓
Data Loader
     ↓
Databricks landing volume
```

---

# 11. Data Loader

A notebook/script called something like:

```text
data_loader.py
```

copies:

```text
staging → landing
```

For example:

```text
staging/batch_0/orders
          ↓
landing/orders
```

It does this for all seven datasets.

The loader also has a **batch parameter/widget**, so you can specify:

```text
batch_0
```

and later:

```text
batch_1
batch_2
```

---

# 12. Verification

After copying the data, the loader checks row counts.

Expected approximate result:

```text
customers       → 5,000
orders          → 20,000
order_items     → 38,000+
products        → 500
categories      → 6
clickstream     → 180,000
inventory       → 45,000
```

The important rule is:

> **Every source should have a non-zero record count.**

This acts as an early health check that:

* Unity Catalog works
* Volumes work
* Files were uploaded
* Copy worked
* Data is present
