# CI/CD Pipeline + UAT Integration Testing — Summary

## 1. Why CI/CD Is Needed

Manual approach would be:

```text
Deploy to UAT manually
        ↓
Run PyTest manually
        ↓
Check result
```

But the project uses the standard automated approach:

```text
Git Push to main
        ↓
GitHub Actions
        ↓
Unit Tests
        ↓
Deploy to UAT
        ↓
Integration Test
```

The pipeline automatically performs deployment and integration testing after changes are pushed to `main`. 

---

# 2. GitHub Actions Workflow

The CI pipeline is defined under:

```text
.github/
└── workflows/
    └── ci.yaml
```

It supports two triggers:

### Automatic

```text
Push → main branch
```

### Manual

```text
workflow_dispatch
```

So the workflow can either run automatically after a main-branch push or be manually triggered. 

---

# 3. Three Jobs in the CI Pipeline

The complete pipeline has three major jobs:

```text
1. Unit Test
      ↓
2. Validate & Deploy UAT
      ↓
3. Integration Test
```

Each stage depends on the previous stage succeeding. 

---

# 4. Job 1 — Unit Testing

GitHub creates an Ubuntu VM.

Steps:

```text
Checkout Code
     ↓
Install Python 3.12
     ↓
Install pytest + PySpark
     ↓
Run Unit Tests
```

PyTest discovers and executes the unit-test files from the project test directory.

If unit tests fail:

```text
STOP
```

Deployment will not happen. 

---

# 5. Job 2 — Validate and Deploy UAT

This job depends on:

```text
Unit Test = SUCCESS
```

It runs on another Ubuntu VM.

## Required Secrets

The pipeline gets these from GitHub Secrets:

```text
DATABRICKS_HOST_UAT
DATABRICKS_TOKEN_UAT
```

They are exposed as environment variables at runtime rather than hard-coded in YAML. 

---

# 6. Install Deployment Dependencies

The UAT deployment VM installs:

```text
Python
Databricks CLI
Databricks SDK
```

The repository is also checked out onto the VM.

---

# 7. Ensure UAT Catalog Exists

Initially, the pipeline attempted to create the UAT catalog using the Workspace API.

That failed when the catalog didn't have an appropriate storage location configured.

The error was related to:

```text
Metastore storage root URL does not exist
```

The solution was to use SQL:

```sql
CREATE CATALOG IF NOT EXISTS UAT
```

through Databricks SQL execution using a warehouse.

A new GitHub secret was therefore added for:

```text
Databricks Warehouse ID UAT
```

The lecture demonstrates this as a real deployment debugging/fix step. 

---

# 8. Validate the Databricks Bundle

After the UAT catalog is available:

```bash
databricks bundle validate --target uat
```

This checks the bundle structure/configuration before deployment.

---

# 9. Deploy the Bundle

Next:

```bash
databricks bundle deploy --target uat
```

This deploys the complete project bundle into UAT.

---

# 10. Run Environment Bootstrap

After deployment:

```bash
databricks bundle run \
  <environment-bootstrap-job> \
  --target uat
```

The bootstrap job prepares the UAT environment.

It creates/initializes things such as:

```text
Catalog
Schema
Landing Zone
Bronze tables
Silver tables
Gold tables
DQ objects
Monitoring objects
```

So the target environment becomes ready for testing. 

---

# 11. Job 3 — Integration Testing

Integration testing starts only when:

```text
Validate & Deploy UAT
        ↓
SUCCESS
```

Then GitHub starts another Ubuntu VM.

Dependencies:

```text
Python 3.12
Databricks CLI
PyTest
Faker
Databricks SDK
```

Faker is required because the integration test generates the fixed test dataset. 

---

# 12. Run Integration Test

The pipeline executes:

```text
tests/integration/test_integration.py
```

using PyTest.

The test performs:

```text
Reset UAT Landing
      ↓
Generate Fixed Test Data
      ↓
Upload Data to UAT
      ↓
Ingestion Full Refresh
      ↓
Transformation Full Refresh
      ↓
Run Orchestration Job
      ↓
Validate Counts / Results
      ↓
PASS / FAIL
```

---

# 13. Complete UAT CI/CD Flow

The final architecture is:

```text
                 Git Push
                    │
                    ▼
              GitHub Actions
                    │
                    ▼
              ┌─────────────┐
              │ Unit Tests  │
              └──────┬──────┘

          ┌──────────────────────┐

          │ Bootstrap UAT        │

          │ Run Orchestration    │
          │ Validate Results     │
          └──────────┬───────────┘
                     │
                 PASS / FAIL
```

# 15. Then Production Comes

After UAT is successfully tested, **production deployment is different**.

We do **not** run the integration test in production because integration testing creates test data. 

Instead:

```text
UAT Integration Test
        ↓
Production Deployment
        ↓
Smoke Test
```

The production smoke test verifies that the deployed components exist and are reachable.

---

# 16. Production Smoke Test

Suggested checks:

```text
✓ Pipeline exists
✓ Latest pipeline update/run didn't fail
✓ Orchestration job exists
✓ Dashboard exists
✓ Gold tables exist
✓ Gold tables are queryable
```

It doesn't insert artificial test data into production. 

---

# 17. Production CI/CD

Production gets a separate workflow:

```text
.github/workflows/
    ├── ci.yaml
    └── deploy-prod.yaml
```

Production workflow:

```text
Manual Trigger
      ↓
Bundle Validate
      ↓
Bundle Deploy → PROD
      ↓
Environment Bootstrap
      ↓
Smoke Test
```

The production workflow is intentionally **manual**, rather than automatically deploying every push to `main`. 

---

# 18. Production Secrets

Production requires separate secrets:

```text
DATABRICKS_HOST_PROD
DATABRICKS_TOKEN_PROD
```

This keeps UAT and production credentials separated.

## 🎯 Most Important Interview Point

Remember the difference:

| Environment    | Testing                                                        |
| -------------- | -------------------------------------------------------------- |
| **Dev**        | Unit testing / development testing                             |
| **UAT**        | **Integration / end-to-end testing with controlled test data** |
| **Production** | **Smoke testing only — no test data**                          |

And the UAT CI/CD sequence is:

**Unit Test → Validate → Deploy UAT → Bootstrap → Integration Test.**
