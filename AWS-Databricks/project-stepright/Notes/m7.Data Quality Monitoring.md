# Data Quality Monitoring — Ordered Summary

## 1. Current Data Quality Setup

The project already has **three major data-quality mechanisms**:

1. **Expectations** — mainly in Silver
2. **Quarantine tables** — bad records are moved to quarantine
3. **Referential integrity metadata/checks**

These work behind the scenes, but there was no proper place for users/operations teams to monitor them. The goal of this chapter is to close that gap. 

---

# 2. Three Things We Need to Monitor

### A. Expectations

During pipeline execution, expectations either pass or fail.

Databricks/Lakeflow records these events in the **event log**.

We can query:

```text
Pipeline ID
     ↓
Event Log
     ↓
flow_progress events
     ↓
Data Quality / Expectations
     ↓
Passed / Failed records
```

The important event type is:

```text
flow_progress
```

because expectation information is available inside its `details`.

---

### B. Quarantine Tables

We already have quarantine tables.

We monitor their record counts:

```text
Quarantine count = 0
        ↓
Good

Quarantine count > 0
        ↓
Some bad records exist

Sudden large increase
        ↓
Potential serious data-quality problem
```

---

### C. Referential Integrity

Databricks/Delta does not strictly enforce the project's parent-child relationships.

So we manually check relationships using:

* `NOT EXISTS`
* Anti-joins

Example:

```text
silver_order_items
        ↓
Does order_id exist?
        ↓
silver_orders
```

If an order item has no corresponding order, it becomes an **orphan/dangling record**.

# 4. Step 1 — Create Event Log Views

Event logs already exist, so nothing needs to be created at the source.

The goal is to create convenient views for the two pipelines:

1. Ingestion pipeline
2. Transformation pipeline

The setup notebook uses three parameters:

```text
catalog
ingestion_pipeline_id
transformation_pipeline_id
```

The catalog defaults to `dev`.

Pipeline IDs are obtained from the respective Databricks pipeline settings and can be passed differently for other environments.

---

# 5. Create Two Raw Event Log Views

For ingestion:

```text
catalog.step_right.ingestion_event_log_raw
```

For transformation:

```text
catalog.step_right.transformation_event_log_raw
```

Conceptually:

```sql
SELECT *
FROM event_log(ingestion_pipeline_id)
```

and:

```sql
SELECT *
FROM event_log(transformation_pipeline_id)
```

The important point is that `event_log` is queried using the **pipeline ID**, so the resulting records belong to that specific pipeline.

---

# 6. Important Event Log Fields

The event log contains fields such as:

```text
event_id
sequence
origin
timestamp
message
level
error
details
event_type
```

There are many event types.

For data-quality monitoring, the important one is:

```text
event_type = 'flow_progress'
```

The `details` field contains the deeper information we need, including data-quality information.

---

# 7. Step 2 — Create Expectations History View

A consolidated view is created:

```text
DQ expectations history
```

It combines:

```text
Ingestion Event Log
        +
Transformation Event Log
        ↓
DQ Expectations History
```

The `details` field is JSON, so the process is:

```text
details JSON
    ↓
flow_progress
    ↓
data_quality
    ↓
expectations array
    ↓
explode array
    ↓
individual expectation rows
```

Each expectation provides information such as:

* Rule name
* Dataset
* Passed records
* Failed records

Then failure rate is calculated:

```text
failure_rate =
failed_records
----------------------------- × 100
passed_records + failed_records
```

The resulting view becomes the source for expectation monitoring.

---

# 8. Why Explode Expectations?

One `flow_progress` event can contain multiple expectations.

Therefore:

```text
One Event
   ↓
Expectations Array
   ↓
explode()
   ↓
Multiple Expectation Rows
```

This gives a flat structure that is easy to query and visualize.

# 10. Step 4 — Referential Integrity View

Another consolidated view is created:

```text
DQ referential integrity
```

Each parent-child relationship is checked independently.

Example:

```text
Orders → Customers
Order Items → Orders
Order Items → Products
Products → Categories
Inventory → Products
Clickstream → Products
Clickstream → Customers
Clickstream → Orders
```

The checks use:

```text
NOT EXISTS
```

or:

```text
ANTI JOIN
```

Example concept:

```sql
SELECT COUNT(*)
FROM silver_orders o
WHERE NOT EXISTS (
    SELECT 1
    FROM silver_customers c
    WHERE o.customer_id = c.customer_id
)
```

The resulting count represents orphan records.

# 16. Dashboard Limitation

The dashboard provides **monitoring**, but not real-time alerting.

For example:

```text
Pipeline running
      ↓
Expectation fails
      ↓
Dashboard gets updated
```

But the dashboard itself doesn't automatically tell the operations team that an expectation has failed.

Therefore, another mechanism is required:

> **Event Hooks**

---

# 17. Step 6 — Event Hooks for Real-Time Alerts

An event hook works like a callback.

Conceptually:

```text
Pipeline generates event
        ↓
Event Hook receives event
        ↓
Custom function analyzes event
        ↓
Condition met?
        ↓
Send alert
```

Possible alert mechanisms:

* Email
* Slack
* Pager
* External API
* Other notification systems

---

# 18. Create Alert Logic

The alert logic is placed in the **utilities** folder so it remains separate from the pipeline code.

Example configuration:

```python
FAILURE_RATE_ALERT_THRESHOLD = 25
```

Meaning:

```text
Failure rate > 25%
        ↓
Send alert
```

---

# 19. `check_expectations_and_alert()`

The function receives the pipeline event.

First:

```text
Is event_type == flow_progress?
```

If not:

```python
return
```

Because expectation information is inside `flow_progress`.

---

# 20. Extract Expectation Information

The function navigates through the event:

```text
event
 ↓
details
 ↓
flow_progress
 ↓
data_quality
 ↓
expectations
```

Then it loops through the expectations.

For every expectation:

```text
passed records
failed records
```

are extracted.

Then:

```text
total = passed + failed
```

and:

```text
failure_rate =
failed / total × 100
```

---

# 21. Trigger Alert

If:

```text
failure_rate > 25%
```

then:

```text
send_alert()
```

is called.

The alert message contains useful information such as:

```text
Pipeline
Expectation name
Dataset
Failure rate
Failed records
Total records
Threshold
```

In the lecture, `send_alert()` only prints the message to the console.

In a real project, it could call:

```text
Email API
Slack API
Pager API
Notification service
External application
```

---

# 22. Register the Event Hook

A separate file is created in the pipeline's `transformations` directory.

It uses:

```text
@dp.on_event_hook
```

This registers a callback with the pipeline.

Conceptually:

```text
Every pipeline event
        ↓
on_event_hook()
        ↓
check_expectations_and_alert()
```

The hook itself doesn't appear as a normal transformation in the pipeline graph. It operates behind the scenes.

---

# 23. Consecutive Failure Safety

The hook supports:

```text
max_allowed_consecutive_failures = 3
```

Meaning:

```text
Hook fails
   ↓
Hook fails
   ↓
Hook fails
   ↓
Disable hook
```

This prevents a broken alerting function from continuously causing problems.

---

## 🎯 Key Interview Takeaways

1. **Expectations** provide row-level data-quality validation.
2. **Quarantine tables** capture bad records for investigation.
3. **Referential integrity** can be monitored using anti-joins/`NOT EXISTS`.
4. **Event logs** provide historical pipeline/event information.
5. `flow_progress` events contain expectation-related information.
6. JSON in `details` can be parsed using `from_json()` and expectation arrays can be exploded.
7. Create **monitoring views first**, then build dashboards on top of them.
8. Dashboard = **monitoring/visualization**.
9. Event hook = **real-time reaction/alerting**.
10. Alert logic should be separated into utility functions.
11. A failure-rate threshold such as **25%** can trigger alerts.
12. `max_allowed_consecutive_failures` provides a safety mechanism for the hook.
13. The same event-hook pattern can be applied to both ingestion and transformation pipelines.
