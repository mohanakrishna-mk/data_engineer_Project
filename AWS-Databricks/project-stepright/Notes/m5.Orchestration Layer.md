# Orchestration Layer — Summary in Order

This lecture completes the **orchestration layer** of the StepRite project. The goal is to run ingestion, quality checks, transformation, and reporting as **one controlled job** instead of manually running two pipelines. 

---

## 1. Existing Architecture

There are already two pipelines:

```text
1. Ingestion Pipeline
   Landing → Bronze

2. Transformation Pipeline
   Bronze → Silver → Gold
```

The problem is that simply doing:

```text
Ingestion
    ↓
Transformation
```

is not enough.

For example, ingestion could technically succeed but ingest **zero records** because a source system was unavailable or a file didn't arrive.

Then transformation would still run and could produce an almost-empty Gold report.

So we need a **health check between the two pipelines**.

---

# 2. Final Job Has 4 Tasks

The decided orchestration is:

```text
Task 1: Ingestion
       ↓
Task 2: Data Quality Gate
       ↓
Task 3: Transformation
       ↓
Task 4: Report
```

### Task 1 — Ingestion

Runs the Bronze ingestion pipeline:

```text
Landing
   ↓
Bronze
   ↓
Bronze Quality
   ↓
Valid / Quarantine
```

### Task 2 — DQ Gate

Checks whether the **overall ingestion run is healthy**.

If there is a systemic problem:

```text
DQ Gate FAIL
    ↓
STOP JOB
```

If everything looks healthy:

```text
DQ Gate PASS
    ↓
Transformation
```

### Task 3 — Transformation

Runs:

```text
Silver → Gold
```

### Task 4 — Report

Produces a summary of what happened during the run.

---

# 3. Important Difference: Row-Level DQ vs Job-Level DQ

This is one of the most important concepts in the lecture.

### Bronze/Silver DQ

These are **record-level checks**.

Example:

```text
One order has invalid data
        ↓
Quarantine/report that record
        ↓
Continue processing other records
```

One bad row should not stop the entire pipeline.

### Orchestration DQ Gate

This is a **run-level/system-level check**.

Example:

```text
Today's Bronze tables = 0 records
```

or:

```text
50%+ records suddenly quarantined
```

That indicates something potentially systemic.

Therefore:

```text
Systemic failure
      ↓
STOP JOB
```

The purpose is to prevent a bad ingestion run from propagating into Silver and Gold.

---

# 4. Environment-Specific Decisions

The job needs to work in:

```text
DEV
UAT
PROD
```

Some values change by environment.

### Schedule

```text
DEV  → Manual
UAT  → Environment-specific
PROD → Recurring schedule
```

### Failure notification

```text
DEV  → No notification
PROD → Failure notification
```

### Pipeline references

The ingestion and transformation pipelines are deployed separately in each environment.

Therefore their IDs/references can change:

```text
DEV
  ↓
UAT
  ↓
PROD
```

These references become deployment variables.

### Catalog

Catalog also changes by environment:

```text
DEV  → dev
UAT  → UAT catalog
PROD → production catalog
```

The lecture's key point is:

> **Identify what changes between environments and make those values deployment variables.**

---

# 5. Develop the Data Quality Gate Notebook

The second lecture implements the DQ gate as a **Databricks notebook**.

It receives two parameters:

```text
catalog
run_date
```

Defaults:

```text
catalog  = dev
run_date = today's date
```

The job will eventually pass these dynamically.

---

# 6. DQ Gate Checks 7 Bronze Tables

The notebook maintains a list of all seven raw Bronze tables.

It also maintains pairs:

```text
Bronze Valid Table
        +
Bronze Quarantine Table
```

Example:

```text
bronze_orders_valid
bronze_orders_quarantined
```

This allows the notebook to calculate:

```text
Valid records
Quarantined records
Total records
Quarantine rate
```

---

# 7. Quarantine Threshold = 50%

The project defines:

```text
quarantine_threshold = 0.5
```

or:

```text
50%
```

Meaning:

```text
Quarantine rate < 50%
        ↓
Continue

Quarantine rate >= 50%
        ↓
DQ Gate FAIL
        ↓
Stop job
```

The threshold is intentionally high because the project doesn't want to stop the entire feed because of a relatively small number of bad records.

---

# 8. DQ Gate — First Check

For every Bronze raw table:

```text
Filter by today's run_date
        ↓
COUNT(*)
```

If:

```text
count == 0
```

then:

```text
FAILURE
```

Reason:

> The ingestion may have failed silently.

A source producing absolutely no data is treated as suspicious.

---

# 9. DQ Gate — Second Check

For every valid/quarantine pair:

```text
Valid Count
+
Quarantine Count
=
Total
```

Then:

```text
Quarantine Rate
=
Quarantine Count / Total Count
```

If:

```text
Quarantine Rate > 50%
```

the notebook records a failure.

---

# 10. Failure Handling

All problems are stored in a:

```text
failures
```

list.

At the end:

```text
if failures:
    print failures
    raise exception
```

Therefore:

```text
Any systemic failure
        ↓
Exception
        ↓
DQ task fails
        ↓
Transformation does NOT run
```

If there are no failures:

```text
DQ Gate Passed
```

and the next task can run.

---

# 11. Develop the Post-Run Report

The final task is a **Python script**:

```text
report.py
```

Its purpose is **not to fail the job**.

It simply summarizes what happened after the pipeline execution. 

The report contains information about:

```text
Bronze
Silver
Gold
Quarantine
```

---

# 12. Report Parameters

The Python script receives:

```text
--catalog
--run-date
```

Important distinction:

### Notebook

Uses notebook parameters/widgets.

### Python script

Uses command-line arguments:

```text
--catalog=dev
--run-date=2026-07-15
```

The script has default values if arguments aren't provided.

---

# 13. Report Counts

The script maintains lists of:

```text
Bronze tables
Silver tables
Gold tables
```

It also maintains metadata describing the appropriate date column.

This is necessary because different layers use different fields.

For example:

### Bronze

Uses:

```text
ingested_at
```

### Silver

Uses:

```text
TSMS
```

and TSMS is epoch milliseconds.

The report therefore has a utility function that builds the appropriate date filter depending on the table's date column/type. 

---

# 14. Total Count vs Today's Count

The report can calculate:

```text
Total count
```

or:

```text
Today's count
```

For example:

```text
Bronze Orders
--------------------
Total: 20,000
Today: 500
```

For Gold, today's count isn't considered meaningful in this report, so Gold uses total counts instead. 

---

# 15. Report Does NOT Fail the Job

This is another important distinction.

If the report cannot read a table:

```text
Report error
```

it returns something like:

```text
-1
```

and prints an error instead of throwing an exception.

Why?

Because the main job has already completed.

The report is only for **observability**, not pipeline control.

So:

```text
DQ Gate
→ Can STOP the job

Report
→ Should NOT STOP the job
```

---

# 16. Quarantine Reporting

The report also calculates:

```text
Valid records
Quarantined records
Total records
Quarantine rate
```

Formula:

```text
Quarantine Rate
=
Quarantined / (Valid + Quarantined)
```

If total records are zero:

```text
Quarantine Rate = 0
```

to avoid division-by-zero.

---

# 17. Final Orchestration Job

After preparing the DQ notebook and report script, everything is stitched together.

### Task 1

```text
Run Ingestion
Type: Pipeline
Pipeline: StepRite Ingestion Pipeline
```

### Task 2

```text
DQ Check
Type: Notebook
Depends on: Run Ingestion
Condition: Run if all succeeded
```

### Task 3

```text
Run Transformation
Type: Pipeline
Pipeline: StepRite Transformation Pipeline
Depends on: DQ Check
Condition: Run if all succeeded
```

### Task 4

```text
Report
Type: Python Script
Depends on: Run Transformation
Condition: Run if all succeeded
```

Final flow:

```text
┌─────────────────────┐
│ 1. Ingestion        │
│ Landing → Bronze    │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 2. DQ Check         │
│ Systemic validation │
└──────────┬──────────┘
           ↓ PASS
┌─────────────────────┐
│ 3. Transformation   │
│ Bronze → Silver     │
│ Silver → Gold       │
└──────────┬──────────┘
           ↓ SUCCESS
┌─────────────────────┐
│ 4. Report           │
│ Run summary         │
└─────────────────────┘
```

---

# 18. Job-Level `run_date`

Instead of passing `run_date` individually to every task, it is defined at the **job level**.

The value comes dynamically from the job's start date:

```text
job.start_time → ISO date
```

Then it is automatically available to the tasks.

This keeps parameter management centralized.

---

# 19. Final Result

The complete StepRite architecture is now:

```text
                 ORCHESTRATION JOB
                        │
                        ▼
              ┌──────────────────┐
              │    INGESTION     │
              │ Landing → Bronze │
              └────────┬─────────┘
                       ↓
              ┌──────────────────┐
              │    DQ GATE       │
              │ Zero rows?       │
              │ Quarantine >50%?│
              └───────┬──────────┘
                      │
                PASS  │  FAIL
                 ↓    └────→ STOP
              ┌──────────────────┐
              │ TRANSFORMATION   │
              │ Bronze → Silver  │
              │ Silver → Gold    │
              └────────┬─────────┘
                       ↓
              ┌──────────────────┐
              │ POST-RUN REPORT  │
              │ Bronze/Silver/   │
              │ Gold/Quarantine  │
              └──────────────────┘
```

## ⭐ Interview-level takeaway

The most important distinction from this lecture is:

```text
Row-level DQ
    ↓
Don't stop pipeline
    ↓
Quarantine / report bad records

Job-level DQ
    ↓
Detect systemic failure
    ↓
STOP pipeline
```

And the final orchestration pattern is:

**Ingestion → DQ Gate → Transformation → Reporting**

This gives the project not only data processing, but also **run-level reliability, controlled dependencies, environment-specific configuration, and observability**.
