## Unit Testing Preparation — Ordered Summary

### 1. Goal of this lecture

The project’s end-to-end pipeline is already complete, but **testing has not yet been implemented**. The focus is to prepare the code so that unit testing is possible. 

There are two types of testing:

1. **Unit Testing**
2. **Integration Testing**

This chapter focuses on **unit testing**; integration testing will be done later after deployment to the test environment. 

---

## 2. What is Unit Testing?

Unit testing means testing the **smallest components** of the pipeline, mainly:

> **Functions that implement business logic**

In Spark/Databricks, these are generally **transformation functions**. 

Example:

```python
def compute_daily_revenue(order_items_df, orders_df, products_df, categories_df):
    # business logic
    return result_df
```

We provide input → call the function → verify the output.

---

## 3. Prerequisites for Unit Testing

A function should have:

### A. Input parameters

The business logic should depend on parameters passed to the function.

```text
Input DataFrames
      ↓
Function
      ↓
Business Logic
```

### B. Deterministic output

Same input should produce the same output.

```text
Same Input → Same Output
```

This makes the function unit-testable. 

---

## 4. Unit Testing vs Integration Testing

| Unit Testing               | Integration Testing                                  |
| -------------------------- | ---------------------------------------------------- |
| Tests individual functions | Tests complete pipeline                              |
| Tests business logic       | Tests dependencies/configuration/components together |
| Usually development stage  | Test environment                                     |
| Input → function → output  | End-to-end execution                                 |
| Fast and isolated          | Environment dependent                                |

# 5. Problem Found in the Gold Layer

The original `gold_revenue` function contained the **pipeline code and business logic together**.

For example:

```python
def gold_daily_revenue():
    # reads Silver tables
    # filters current SCD2 records
    # calculates order subtotals
    # allocates discounts
    # aggregates revenue
    # returns DataFrame
```

The problem:

```text
gold_daily_revenue()
        ↓
No parameters
        ↓
Directly accesses Databricks/Silver tables
        ↓
Business logic cannot easily be unit tested
```

The materialized-view pipeline requires the function to have this structure, so the business logic needs to be separated. 

---

# 6. Refactoring Approach

The solution is:

> **Separate pipeline code from business logic.**

Create:

```text
gold_revenue.py
gold_revenue_logic.py
```

### Pipeline file

```python
def gold_daily_revenue():
    return compute_daily_revenue(
        order_items_df,
        orders_df,
        products_df,
        categories_df
    )
```

### Logic file

```python
def compute_daily_revenue(
    order_items_df,
    orders_df,
    products_df,
    categories_df
):
    # business logic
    return result_df
```

Now:

```text
Databricks Pipeline
       ↓
gold_daily_revenue()
       ↓
compute_daily_revenue()
       ↓
Business Logic
       ↓
DataFrame
```

The pipeline function remains compatible with the materialized view, while `compute_daily_revenue()` can be independently unit tested. 

---

# 7. Why This Refactoring Works

Before:

```text
Pipeline
   +
Business Logic
   +
Databricks Dependencies
   ↓
Hard to Unit Test
```

After:

```text
Pipeline Code
     ↓
Calls
     ↓
Business Logic Function
     ↓
Input Parameters
     ↓
Deterministic Output
```

Therefore:

```text
compute_daily_revenue()
        ↓
Unit Test
```

The lecture emphasizes that the same refactoring approach should be applied throughout the project. 

---

The same approach was applied to all five Gold transformations:

| Gold Layer  | Business Logic Function         |
| ----------- | ------------------------------- |
| Revenue     | `compute_daily_revenue()`       |

```python
def compute_fulfillment_health(orders_df, sla_days=5):
    ...
```

So the business logic is outside the pipeline and receives its dependencies as parameters.

# 9. What About Silver?

In this project, **Silver does not require unit testing** because it mainly contains:

* Data quality rules
* Type casting
* Declarative pipeline code
* Auto CDC
* Streaming tables/views

There isn't significant custom business logic being implemented as Python/Spark functions. 

However, if Silver contained custom:

```text
Joins
Transformations
Business Rules
Custom Spark Functions
```

then those could also be refactored and unit tested.

---

# 10. What About Bronze?

Most Bronze code also doesn't require unit testing.

Bronze mainly:

```text
Source/Landing
      ↓
Auto Loader
      ↓
Raw Bronze
```

It is primarily ingestion/copy logic and is dependent on Databricks resources such as volumes and Auto Loader. 

Such environment-dependent code is better covered by **integration testing**, rather than unit testing.

---

# 11. Important Exception — Bronze Quality Function

There was one independent function in Bronze:

```python
quarantine_rule(rules)
```

Its job is to:

```text
Rules dictionary
      ↓
Build SQL expression
      ↓
Return SQL expression
```

This function does **not** depend on Databricks.

Therefore, it **can be unit tested**.

So unit testing is not limited only to Gold. The important question is:

> **Does the function contain independently testable business logic, without requiring a Databricks environment?**

---

# 12. Main Rule to Remember

When deciding whether to unit test a function, ask two questions:

### Question 1

**Am I testing business logic?**

If yes → good candidate.

### Question 2

**Does this function require the Databricks environment to execute?**

If yes → don't make it a unit test.

Instead, it belongs more naturally in **integration testing**.

## 🎯 Interview Takeaway

The key concept from this lecture is:

> **Design transformation/business logic as small, parameter-driven, deterministic functions, and keep Databricks pipeline code thin.**

This gives:

```text
Thin Pipeline
      ↓
Business Logic Function
      ↓
Input Parameters
      ↓
Deterministic Output
      ↓
Easy Unit Testing
```

And remember:

**Databricks-dependent code → Integration Testing**

**Independent business logic → Unit Testing**
